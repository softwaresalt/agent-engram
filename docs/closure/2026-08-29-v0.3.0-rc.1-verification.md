## Verification boundary

This record separates evidence available before a tag exists from checks that
can only run against hosted release assets. G1 does not create a local or
remote tag, upload an asset, or publish or edit a GitHub Release.

| Evidence class | Meaning |
|---|---|
| Pre-tag static evidence | Source, workflow, and local package checks that can be completed at G1 |
| Post-publish required | Proof that must come from the exact hosted archives after separate G2 and G3 approvals |

The `-dirty` build suffix identifies this as pre-commit G1 evidence, not a
hosted release asset. The version value came from the unpacked archive binary.
Only the G3 rerun against the clean, tagged, hosted archive can prove the final
asset.

The version-generic verifier is:

```text
python scripts/verify-release-archive.py \
  --archive <archive> \
  --tag <vMAJOR.MINOR.PATCH[-PRERELEASE]> \
  --target <target-triple> \
  --work-dir <new-empty-directory> \
  [--mcp]
```

### Tier 3 - MCP stdio checks

On Linux and Windows, add `--mcp`. The verifier sends `initialize` and
`tools/list` to the unpacked archive binary. It requires:

* an `initialize` result with `serverInfo` and `protocolVersion`
* a non-empty `tools` array
* JSON-only stdout
* bounded exit after stdin closes, with no panic

The check deliberately passes a nonexistent workspace. The serve-first shim
must still answer `initialize` and `tools/list`, then exit with the documented
`admission_failure` code `10`. This isolates MCP stdio behavior from the known
daemon-readiness defect and does not turn a readiness timeout into an RC gate.
The verifier prints `MCP_PROTOCOL_VERSION`, `MCP_TOOL_COUNT`, and
`MCP_STDIN_CLOSE_EXIT` for the evidence record.

### Healthy signals, failure signals, and monitoring

Healthy signals are stable tag and asset identities, successful native archive
smokes, at least 90% of expected workspaces Ready within 10 minutes, no fresh
or at-most-25 MB workspace missing the unchanged 30-second window, zero
accepted crashes or stale-state cleanup, and successful supported-platform MCP
compatibility.

Failure signals are any tag/body/asset identity drift, digest mismatch,
archive or MCP smoke regression, index or database corruption, actionable
shipped-path security advisory, supported-platform incompatibility, readiness
below the numeric thresholds, or crash/stale-state thresholds defined in the
rollback and observability decision.

The release owner records every startup, database size, cold/warm
classification, time-to-Ready, exit status, and compatibility result using
existing structured logs, daemon/workspace status, startup-failure records,
and manual reports. The authoritative baselines, numeric alert thresholds,
queries, and cadence are in the linked rollback and observability decision.
There is no centralized dashboard; this is a structured manual observation
plan.

### Rollback trigger and procedure

**Trigger:** apply the first matching numeric or immediate-withdraw criterion
in the rollback and observability decision, including any corruption or
credible security issue, supported artifact incompatibility, readiness below
threshold, or crash/stale-state threshold.

**Procedure:** stop recommending the RC, preserve diagnostics, and obtain
separate explicit approval before changing the GitHub Release or tag. Prefer
converting the RC to a draft. If deletion is separately approved, delete only
the RC release and RC tag; never alter `v0.2.0`. Publish a withdrawal notice
and use `rc.2` only after the trigger has a verified disposition.
