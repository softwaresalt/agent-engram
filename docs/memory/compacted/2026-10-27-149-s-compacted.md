## Outcome

Shipment 149-S delivered `142.064-T` (PRE-3c), the last slot of the PRE-3 family: the activation driver
`drive_generation_activation` now re-attempts the SAME published revision when its last failure is
`RejectionClass::Transient` (`TransientRetry`: 100 ms doubling, 2 s cap backoff; window of
`layout.activation_deadline` measured from the revision's first transient failure). A permanent
rejection is never re-attempted; a newer revision starts a fresh window. Feature PR #429 merged with
merge commit `bd40390445fd083dc64913c0c646008a82c88d1e`.

## Decisions

* RED first: `read_server_retries_a_transient_failure_of_the_same_revision` failed against
  `Worker: 142.064-T`; the precondition `an_absent_inventory_file_is_classified_transient` proves the
  absent inventory file is `Transient` by `classify`.
* The driver tick `delay` is set to the retry backoff after a transient failure so the 100 ms schedule
  is not hidden by the loop's own capped delay (local review round 1, P2).
* The failure timestamp is captured before the awaited manifest recheck, so a slow recheck cannot extend
  the retry window (Copilot round 1, medium).

## Learnings

* PRE-3 close evidence: three identical full-output runs of `integration_read_server_generation_wiring`
  (10 cases) and all 8 consumer targets matching the `142.076-T` baseline.
* Wall-clock tests flake on this loaded host: `integration_backlog_hydration::backlog_index_100_items_under_5_seconds`
  (5.0-8.9 s), `hcl_indexing_test` cold start and `integration_read_server_lifecycle` each failed once and
  passed on rerun or in CI.
* The engram daemon (PID 37676) stayed in `starting` and never reached `ready`, so runtime probes were
  blocked again (existing stash `6B3DD712`).
