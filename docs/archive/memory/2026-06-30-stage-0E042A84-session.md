(Daemonless) Mode for Indexing Operations") / shipment **`030-S`**. Fabricating

## Evidence (grounded in real files)

Code — the capability exists today:
- `src/bin/engram.rs` — clap subcommands `Index { direct }` and
  `Sync { full, direct }` with `--direct` flag + `ENGRAM_DIRECT=1` env
  (`BoolishValueParser`); `INDEXING_TIMEOUT_SECS = 300`.
- `src/cli/commands/indexing.rs` — `run_index` / `run_sync` route to
  `run_direct_sync` when `direct` is set.
- `src/cli/direct.rs` — `run_direct_sync()`: acquires `DaemonLock` (exit 2 if a
  daemon is running), pre-probes the CozoDB advisory lock (fast exit 2), calls
  the **same** service function the daemon uses
  (`index_workspace_with_progress` / `sync_workspace_with_progress` from
  `src/services/code_graph.rs`), persists to the resolved data dir
  (`.engram/` via `resolve_data_dir`), and emits a JSON-RPC 2.0 envelope with
  field-for-field parity. Exits on completion.
- `src/cli/runner.rs` — the daemon IPC path + friendly `IndexInProgress`
  messaging (the daemon-timeout pain that `--direct` was built to sidestep).

Tests — `tests/integration/cli_direct_test.rs`: exit-0 on empty workspace,
JSON-RPC envelope shape, `ENGRAM_DIRECT=1` activation, non-git rejection
(exit 2), Windows DB-lock contention (exit 2). Plus unit tests in
`src/cli/direct.rs` (result-JSON parity, cross-handle fd_lock).

Backlog — prior delivery:
- Feature `045-F` + tasks `045.001-T`..`045.004-T` (runner module, `--direct`/env
  wiring, integration tests, freshness detection so the daemon skips re-index
  after a direct run).
- Shipment `030-S` "CLI-Direct Daemonless Mode".
- Follow-up hardening `047.004-T` / `047.007-T` (guard `--direct` vs
  daemon-held DB).
- Archived plan `docs/archive/plans/2026-05-08-cli-direct-daemonless-mode-plan.md`
  whose Problem Frame matches this stash near-verbatim (30s IPC timeout, opens
  CozoDB directly, persists, exits).
