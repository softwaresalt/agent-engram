# Execution Plan — v0.3.0-rc.1 Prerelease (Dogfood RC)

* **Backlog feature**: `139-F`
* **Date**: 2026-08-29
* **Base commit**: `bdda5aac8e6326d646e3b30d3144e4349db770a9` (`main`, clean, synchronized)
* **Prior public release**: `v0.2.0` (stable, 2026-06-16); `main` is ~1,409 commits ahead
* **Operator decision**: create `v0.3.0-rc.1` now for dogfooding; do **not** represent it as
  stable. Stable `v0.3.0` remains blocked on server reliability work.

---

## 1. Problem Frame

There is no consumable, versioned artifact reflecting three months of work on `main`.
Dogfood users are stuck on `v0.2.0`. We need a prerelease that is honest about its
maturity rather than a stable release that overclaims.

The forcing constraint is that engram currently has a **known, reproduced, unfixed
reliability defect**. Live dogfood verification on 2026-08-29 failed:
`engram workspace-status` and indexed search both timed out because the daemon did not
reach Ready within the 30-second readiness window. The queued high-priority spike
`002-SP` documents the underlying behavior — roughly a 7.5-minute cold open of a 135 MB
Cozo database, ~1.37 GB resident, ~893 CPU-seconds, while reporting `starting` across
repeated 30-second readiness windows.

That defect is **not** fixed by this release unit. It is disclosed by it.

## 2. Scope

### In scope (release mechanics only)

1. Version bump surfaces per current cargo-release / Release workflow conventions.
2. Curated release notes / changelog covering meaningful change themes since `v0.2.0`.
3. Explicit prerelease labeling and disclaimer, referencing `002-SP`.
4. Focused smoke gates for packaged cross-platform binaries and MCP stdio behavior,
   layered on the mandatory existing quality/release workflow checks.
5. Rollback/withdraw criteria and release observability signals.
6. Release workflow / tag semantics and prerelease-not-latest verification.
7. Branch/PR approval boundary enforcement.

### Explicitly out of scope

| Excluded | Why |
|---|---|
| Daemon readiness / Cozo cold-start remediation | Tracked by `002-SP`. Widening this unit into reliability implementation is prohibited. Raising the readiness timeout is explicitly not an acceptable remediation. |
| MCP / RMCP modernization | engram resolves `rmcp` 1.8.0; upstream is 3.1.4. VS Code Copilot currently uses MCP 2025-11-25; MCP 2026-07-28 support remains planned. Touch only if existing release mechanics require *metadata*. |
| crates.io publication | `publish = false` in both `Cargo.toml` and `release.toml`. Distribution is GitHub Releases only. |
| `x86_64-apple-darwin` artifact | Intentionally absent from the build matrix (ONNX Runtime prebuilt gap for the embeddings feature). Document as a known limitation; do not add. |
| `002-SP`, `128-F`, `129-F` | Unrelated queue artifacts. Reference `002-SP` only; modify none of them. |

## 4. Decisions

### D1 — Do not use the cargo-release execute path

**Decision**: perform the version bump as ordinary edits on a release branch, or run
cargo-release strictly dry-run / `--no-push --no-tag`. Tag creation is deferred to the
operator-gated task.

**Rationale**: `release.toml` is configured for an unattended maintainer-driven release
(F2). Using it here would silently convert an approved *staging* action into an
unapproved *publish* action, violating requirement 7.

**Rejected alternative**: edit `release.toml` to set `push = false`. Rejected — it mutates
shared release configuration for a one-off constraint and would silently change behavior
for future stable releases. Record the deviation in the PR description instead.

### D2 — The published body must be curated, sourced from `CHANGELOG.md`

**Decision**: author a curated `[0.3.0-rc.1]` section in `CHANGELOG.md`, then confirm the
Release workflow actually publishes it. Remediation ladder, stop at the first that works:

1. Dry-run `git-cliff --latest --strip header` locally against a local tag. If the output
   is already curated and readable, change nothing.
2. Otherwise, minimally change the `changelog` job to source the body from the curated
   `CHANGELOG.md` section.
3. Adding a `cliff.toml` only if it is the smaller change and still yields a curated body.

**Rationale**: F3 + F4 together mean the default path plausibly publishes either an empty
body or an unreadable 1,409-commit wall. Requirement 2 forbids both.

**Constraint**: any workflow edit stays inside the `changelog` job and preserves SHA-pinned
actions, workflow-level `permissions: contents: read` with `contents: write` only on the
`release` job, and `persist-credentials: false` on checkouts.

### D3 — Readiness is disclosed, not gated on

**Decision**: no RC smoke gate may depend on the daemon reaching Ready against a large
existing database. Readiness-dependent checks, if run at all, use a fresh/empty workspace
and are recorded as informational only.

**Rationale**: the defect is known and unfixed. Gating the RC on it would either block the
RC indefinitely or create pressure to "fix" it by raising the timeout — which `002-SP`
explicitly rules out.

### D4 — Stable `v0.3.0` block must be falsifiable

**Decision**: the rollback/observability doc states concrete reliability acceptance gates
that unblock stable `v0.3.0`, and those gates must not be satisfiable by increasing the
readiness timeout.

**Rationale**: "blocked on reliability work" without exit criteria is an indefinite hold.

            │        ^        │
139.003-T ──┘────────┘        ├──> 139.005-T

* `139.005-T` last — needs the curated body (`139.002-T`) and the smoke checklist (`139.004-T`).

## 8. Rollback Posture

This unit is cheap to reverse. Nothing is published to crates.io (`publish = false`), so
withdrawal is: mark the GitHub Release draft or delete it, delete the tag (destructive —
operator approval required), and note the withdrawal in `CHANGELOG.md`. The invariant
throughout is that **`v0.2.0` remains untouched and remains Latest**. Full criteria are
defined in `139.003-T`.

## 9. Ship Dispatch Constraints

* Ship executes `139.001-T` → `139.005-T` in dependency order on a single release branch.
* Ship may open the release PR and drive CI to green without further approval.
* Ship **must not** merge the PR, create or push the tag, or publish/edit the release
  without explicit operator approval at gates G2 and G3.
* If the operator is unavailable, Ship stops and leaves the PR open.
* Ship must not modify `002-SP`, `128-F`, `129-F`, or `release.toml`.
