# Plan Hardening Addendum — v0.3.0-rc.1 Prerelease

* **Backlog feature**: `139-F`
* **Base plan**: `docs/exec-plans/2026-08-29-139-f-v0.3.0-rc.1-prerelease-plan.md`
* **Date**: 2026-08-29
* **Trigger**: elevated blast radius — public binary distribution, release workflow
  surface, immutable tag semantics, and public-facing maturity claims.

Hardening is applied because the artifacts leave the repository. A backlog mistake is
retractable; a published binary with a wrong maturity claim is not.

---

## H1. Blast-Radius Assessment

| Surface | Reversible? | Notes |
|---|---|---|
| `Cargo.toml` / `Cargo.lock` version | Yes | Ordinary revert |
| `CHANGELOG.md` | Yes | Ordinary revert |
| `.github/workflows/release.yml` (`changelog` job, conditional) | Yes | Touches the release path for *all future releases*, not just this one — highest-leverage edit in the unit |
| Git tag `v0.3.0-rc.1` | **Effectively no** | Deleting a pushed tag is destructive and breaks anyone who fetched it |
| GitHub Release + attached binaries | **Effectively no** | Binaries may be downloaded within minutes of publication |
| "Latest release" pointer | Yes, but with public exposure window | Any period where the RC shows as Latest is a period where engram is misrepresented as stable |

**Conclusion**: the last three rows justify hard operator gates rather than agent judgment.

## H2. Failure Modes Not Covered by the Base Plan

### H2.1 — Empty release body published silently

`generate_release_notes: false` + `draft: false` means the release publishes whatever the
`changelog` job emitted, including nothing. The workflow has no assertion that the body is
non-empty; `softprops/action-gh-release` will happily publish an empty body.

**Hardening**: `139.005-T` must confirm the `changelog` job output is non-empty **in the
run log** before declaring publish successful. If the body published empty, that is a
withdraw-and-redo condition, not an "edit it afterwards" condition — because the
disclaimer is the point of the release.

### H2.2 — The disclaimer exists but nobody sees it

A disclaimer buried under 20 bullets of change themes is functionally absent on a GitHub
Releases page.

**Hardening**: disclaimer must be the **first** content block in the `[0.3.0-rc.1]`
section, above `### Added`. Enforced in `139.002-T` implementation notes.

### H2.3 — `git-cliff` succeeds but produces the wrong range

`git-cliff --latest` derives its range from tag ordering. With `v0.1.0`, `v0.2.0`, and a
new prerelease tag, `--latest` may or may not resolve to `v0.2.0..v0.3.0-rc.1` depending on
git-cliff's prerelease handling.

**Hardening**: the `139.002-T` dry-run must record not just the output but the **commit
range git-cliff selected**. A plausible-looking body over the wrong range is worse than an
empty one.

### H2.4 — Version bump does not reach the shipped binary

A stale build cache, a workspace-member mixup, or a lock not regenerated could produce a
binary still reporting `0.2.0`.

**Hardening**: already covered — `139.004-T` Tier 2 asserts `engram --version` reports
`0.3.0-rc.1` **from the unpacked release archive**, not from a local build. This is the
single most valuable smoke assertion in the unit; do not let it be substituted with a
local `cargo run --version`.

### H2.5 — Retry after a mistaken tag

The Release workflow uses `concurrency: release-${{ github.ref }}` with
`cancel-in-progress: false`. A mistaken or premature tag cannot simply be re-pushed;
cleanup requires tag deletion and release deletion.

**Hardening**: tag/release deletion is classified **destructive** under Constitution
Principle V and requires its own operator approval. Ship must not self-serve a retry.

### H2.6 — Prerelease semantics regression in a future stable release

If `139.002-T` takes remediation path 2 or 3 (editing the `changelog` job or adding
`cliff.toml`), that change persists into the next **stable** release, where the body
requirements differ.

**Hardening**: any such edit must be additive and neutral for stable tags. If sourcing the
body from `CHANGELOG.md`, the mechanism must key off the tag version generically, not
hardcode `0.3.0-rc.1`. Called out explicitly at review.

### H2.7 — Reliability defect understated

There is a real temptation to soften "the daemon did not reach Ready within 30 seconds and
a 135 MB database took ~7.5 minutes to open" into "startup may be slow on large
workspaces."

**Hardening**: `139.002-T` acceptance criteria require the **concrete measured numbers**
and the explicit statement that raising the readiness timeout is not an accepted
remediation. Vague phrasing is a review-blocking finding.

## H3. Strengthened Gate Definitions

| Gate | Precondition | Approver | Failure action |
|---|---|---|---|
| **G0 — scope freeze** | Plan reviewed; freeze-scope declared | Stage | Halt if any task proposes reliability implementation |
| **G1 — PR green** | `139.001-T`–`139.004-T` done; all mandatory CI gates green; `git-cliff` dry-run output + selected range recorded in PR | Ship (self) | Fix forward, max 3 review-fix cycles |
| **G2 — merge** | G1 complete; operator has read the curated body and the disclaimer | **Operator only** | Leave PR open. Do not self-approve. Do not wait-and-retry. |
| **G3 — tag & publish** | G2 complete; pre-tag static verification items 1-5 checked | **Operator only** | Leave `main` merged and untagged. This is a safe resting state. |
| **G4 — post-publish** | Release published | Ship verifies, operator confirms | If RC shows as Latest, correct immediately and file a defect |

`main` merged-but-untagged is explicitly a **safe resting state**. Ship must be comfortable
stopping there indefinitely.

## H4. Additional Prohibitions for Ship

1. Do not run `cargo release` with `--execute`, in any form, for any reason.
2. Do not modify `release.toml`.
3. Do not modify `002-SP`, `128-F`, or `129-F`.
4. Do not add `x86_64-apple-darwin` to the build matrix.
5. Do not change the readiness timeout, anywhere, for any reason — including "just for the
   smoke test."
6. Do not upgrade `rmcp` or any MCP protocol constant.
7. Do not bump `crates/powerbi-tmdl-parser`.
8. Do not run a broad `cargo update`.
9. Do not delete or re-point the `v0.2.0` tag or release.
10. If a new defect is discovered, stash it. Do not fix it in this unit.

## H5. Residual Risk Accepted

* The RC ships with a known, unfixed, high-impact reliability defect. This is **accepted
  deliberately** and is the reason the release is a prerelease. The mitigation is
  disclosure quality, not remediation.
* Dogfood signal quality depends on manual reporting for several observability signals,
  since adding instrumentation is out of scope. Accepted; noted in `139.003-T`.
* MCP compatibility against current VS Code Copilot (MCP 2025-11-25) is verified only by
  smoke-level `initialize` / `tools/list`, not by full client interop. Accepted for an RC.
