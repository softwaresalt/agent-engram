# Deliberation — 090.005-T CLI<->MCP routing-identity + compiler-checked dispatch registry (defer)

- **Date:** 2026-07-31
- **Cycle:** Stage drain-closeout (branch `101-drain-closeout`)
- **Source task:** 090.005-T (task/low; parent 090-F archived)
- **Disposition:** DEFER as a future feature. Task parked to `blocked`; NOT
  scheduled into a shipment this cycle.

## Problem frame

The existing CLI<->MCP parity drift guard (090.002-T, in
`tests/contract/lint_dax_cli_parity_test.rs`) proves existence and documentation
parity, and it already enforces the known feature-gated tools through
`MCP_WITHOUT_CLI_ALLOWLIST` and `mcp_gap_allowlist_matches_documented_gap_rows`
(verified at test lines 21 and 337). PR #259 Copilot review raised two residual
gaps the current guard does not cover.

- **T5 — routing identity.** `every_documented_cli_command_resolves_to_help`
  (verified at ~line 388) proves only that a documented CLI command has a
  `--help` page. It does not prove the command invokes the mapped MCP
  method/handler. A handler could be re-pointed (for example `engram health`
  routed to `get_workspace_statistics`) while every parity test stays green.
  There is no structured CLI-command -> MCP-method registry today; the CLI
  handlers in `src/cli/commands/*.rs` (10 files, verified) call services/IPC
  directly, not a one-to-one method table.
- **T6 — dispatch completeness.** `dispatch_tool_names()` (verified at ~line
  147) text-parses the `src/tools/mod.rs` dispatch match by line. A new
  feature-gated dispatch-only arm wrapped across lines by rustfmt would be
  omitted, and since such a name is absent from `all_tools()`, neither the
  superset oracle nor `every_dispatch_tool_is_documented_as_mapped_or_allowlisted_gap`
  (verified at ~line 302) would catch it. Present exposure is bounded: the known
  feature-gated tools (`query_changes`, `index_git_history`) are allowlist-
  enforced, so only a hypothetical FUTURE feature-gated tool is exposed.

## Blast radius

The deliverable touches the dispatch single source of truth in
`src/tools/mod.rs` (`dispatch` @ ~249, `should_record_metrics` @ ~63, verified),
a new structured CLI -> MCP method mapping consumed by the parity contract test,
and potentially every `src/cli/commands/*.rs` handler to thread routing
identity. That is cross-cutting: tool dispatch identity, a test contract, and
the CLI surface at once. This is elevated blast radius under the impl-plan /
plan-harden rubric.

## Options

- **Option A — build now as a low task.** Rejected. The deliverable is a
  compiler-checked dispatch-name registry (single source of truth, feature-gated
  names included, consumed by BOTH dispatch and the guard) plus a structured
  CLI -> method mapping asserting routing identity. None of this exists today; it
  is a new subsystem. It cannot be honestly bounded to a single sub-2h,
  width-isolated task, and it would mix tools-dispatch work with test-contract
  work and CLI-surface work — a width-isolation violation.
- **Option B — defer as a future feature.** Promote to a first-class feature when
  a trigger fires. Scope it with its own impl-plan plus plan-harden (elevated
  blast radius) and decompose into at least two width-isolated sub-2h tasks:
  introduce the compiler-checked dispatch-name registry; make dispatch and the
  guard consume it; add the CLI -> MCP method mapping and the routing-identity
  assertion.
- **Option C — hold at the status quo guard.** Zero work. The residual gaps
  persist: a re-pointed handler or a future feature-gated dispatch-only tool
  would not be caught. Acceptable short term because the present exposure is
  hypothetical.

## Chosen direction

DEFER as a future feature (Option B), holding at Option C until a trigger fires.

1. There is no live defect. The known feature-gated tools are already
   allowlist-enforced; the uncaught cases are hypothetical (a future
   feature-gated dispatch-only tool, or a deliberately re-pointed handler).
2. The blast radius is elevated and cross-cutting, so this needs plan-harden and
   a real decomposition, not a low-priority pick-up-ready task. Leaving it as a
   `queued` task under the archived 090-F misrepresents a new-subsystem feature
   as ready cleanup.
3. Introducing the registry and asserting routing identity requires compiling and
   running the contract suite, which is Ship/build-executed and out of Stage's
   hands-on scope. Stage records the shape and defers.

Revisit triggers:

- a new feature-gated MCP tool is added, making the T6 exposure real; or
- a CLI handler is intentionally re-pointed, or an incident shows routing drift,
  making the T5 exposure real; or
- an unrelated refactor of `src/tools/mod.rs` dispatch makes the registry cheap
  to introduce as a side effect.

## Open questions (for the future plan)

1. Should the dispatch-name registry be a `const`/`static` slice or a generated
   macro table, and can it be shared with `all_tools()` without a cyclic
   dependency?
2. What is the authoritative CLI-command -> MCP-method mapping source: a
   hand-maintained table, or a value derived from each command handler?
   Derivation is stronger but requires each handler to expose its target method.
3. Can routing identity be asserted without invoking the network/IPC path (a
   pure mapping assertion), to keep the contract test hermetic?
