## The incident (what actually happened)

During 139-S post-merge closure:

1. `checkpoint-20260913-034100.json` (`agent: ship`, phase
   `closure-pr-merge-gate-halt-operator-pause`) was `active`.
2. PR #394 (base `main`, head `post-merge/139-s-…`) **merged** at
   `5638122691796b1502bd55768ea41ac7adc60143`.
3. **After** that merge, commit `43e70430` on the *same, already-merged* branch
   marked the checkpoint resolved.
4. Commits added to a branch after its PR merged never reach `main`. `main`
   continued to report the checkpoint `active`.
5. Remediation required an entirely new pull request, **PR #395**.

## Verified live-contract facts

Every fact below was read from `origin/main` @ `9ab53499` during this session.
None is inherited from PR #396.

**F1 — Checkpoint state is git-tracked.** `git ls-files .backlogit/checkpoints/`
returns **24** tracked files. Resolution therefore mutates a tracked file and
**requires a commit to reach `main`**.

**F2 — There is no non-mutating resolve.** `backlogit checkpoint --help` exposes
`abandon | cleanup | create | get | list | quarantine | resolve`.
`backlogit checkpoint resolve <filename>` takes no flags beyond `-h`. No command
resolves a checkpoint without mutating the tracked file.

**F3 — Resolution is specified only at Session end.** `_ship.agent.md`
§"Session end" item 2 (line 1058) reads, verbatim and in full:

> When the `backlogit` capability pack is installed and the registry advertises
> checkpoint recovery operations, resolve any still-active checkpoints from the
> current session with `backlogit_resolve_checkpoint`. When merge approval or
> closure work must survive a context-window shutdown, leave at most one final
> best-effort checkpoint written via `backlogit_create_checkpoint` with a clear
> `resume_hint`.

It states **no ordering constraint** relative to any PR or merge, **does not
require the resulting mutation to be committed**, and **does not prohibit doing
it on an already-merged branch**. Note the second sentence: the same item also
**creates** a checkpoint, which is the creation source analysed in RR-2.

**F4 — Step 6 never resolves checkpoints.** Ship Step 6 / 6.0 contain no
checkpoint-resolution instruction. Step 6.0 item 4 reads: *"**After all closure
work is committed**, push the branch and create a PR."* Step 6.0 item 5: *"Await
operator approval for the closure PR before merge… Never merge closure work
automatically."*

**F5 — The defect is symmetric.** `_stage.agent.md` §"Session end" item 2 carries
**identical** text to Ship's. Stage has the same latent exposure.

**F6 — No expected-HEAD merge flag exists.** `github-pr-automation.instructions.md`
§1.9 pins review to HEAD by *record comparison* — §1.9.4 Check 1 compares the
readiness block's `Reviewed HEAD` against live `headRefOid` and halts when
stale. There is **no** `--match-head-commit` mechanism. Any plan asserting one
would be fabricating an input.

**F7 — P-022 does not exist.** `git grep P-022 origin/main -- .github` returns
nothing. The authoritative policy catalog is `.github/policies/workflow-policies.md`
(which defines through P-021). This restage **does not mint a new policy ID**.

**F8 — The agent contracts are generated artifacts, and their templates are not
in this repository.** This is the single most consequential constraint on this
unit and it must not be glossed.

- `.github/agents/_ship.agent.md` ends with: *"Generated by autoharness |
  Template: ship.agent.md.tmpl"*.
- The template lives at
  `.copilot/installed-plugins/autoharness/autoharness/templates/agents/_ship.agent.md.tmpl`
  and carries the **same defective Session-end text at line 1060**.
- `.copilot/` is **gitignored** — `git ls-files .copilot/` returns **0**. The
  templates are an installed plugin, not repository source.
- `.github/agents/` **is** tracked (`_orchestrator`, `_ship`, `_stage`, and
  subagents all appear in `git ls-files`).

Consequence: editing `.github/agents/*.md` in this repository **does** change the
contract the agents actually read, and **is** durably committed — but a future
`autoharness install` or `autoharness tune` regenerating from the unchanged
upstream template would revert it, silently re-opening the defect.

## Root cause

The defect is **not** a missing durability mechanism. It is a **missing ordering
constraint**.

Resolution mutates a tracked file (F1, F2), but the only step that performs it
(F3) runs at Session end — after Step 6 item 10's `git checkout main; git pull`,
i.e. after the carrying PR has merged. The contract therefore *instructs* the
agent to produce a mutation at a moment when no open PR can carry it. PR #395
was the inevitable consequence, not an anomaly.

Three concrete gaps:

- **G1 (ordering)**: resolution is unordered with respect to the carrying PR's
  final reviewed HEAD.
- **G2 (prohibition)**: nothing forbids creating the resolution commit on an
  already-merged branch.
- **G3 (verification)**: nothing verifies the resolution actually reached `main`.

## Decision

### D1 — The mandatory release unit is the ordering fix, scoped to committed non-terminal checkpoints

**Question posed**: does strict pre-merge ordering, combined with the existing
current-HEAD review/approval gates, solve the original defect on its own?

**Answer: yes — for the checkpoint class this unit covers, which is explicitly
bounded.** Independent plan review (round 1) established that an unqualified
"always published" claim is false, so the scope is stated precisely here.

**In scope — the *committed non-terminal* class.** A checkpoint whose state file
is committed to the carrying branch *before* that branch's PR reaches its final
reviewed HEAD. For this class, closing G1+G2+G3 is sufficient and complete:

- resolution is performed **before** the carrying PR's final reviewed HEAD, so
  the mutation rides the same reviewed, approved merge;
- creating a resolution commit that cannot reach `main` is **prohibited**;
- landing on `origin/main` is **verified**.

This class covers the mechanism that produced the incident: commit `43e70430`
was a resolution commit added to a branch after its PR merged.

**Out of scope — the *terminal pause* class.** A checkpoint created *after* its
carrying PR's final reviewed HEAD — paradigmatically the
`closure-pr-merge-gate-halt-operator-pause` checkpoint written while awaiting
approval. By construction it can ride no PR. Round-1 review correctly identified
that any attempt to force this class into the ordering fix produces a
contradiction, because the only terminations available are (a) leave it active
on `main`, which re-arms the Session-start fail-closed operator halt on every
later session, or (b) publish it via a further PR, which regenerates the same
pause condition — an unbounded recursion.

Resolving that requires deciding **whether intra-session pause checkpoints
should be committed to a tracked path at all** — a substrate question, not an
ordering question. It is therefore deferred whole to D3. **This unit makes no
claim about the terminal pause class and adds no handling for it.**

No new persistence substrate, marker, tag, ruleset, or repository setting is
required for the in-scope class. The existing §1.9 Reviewed-HEAD staleness halt
(F6) and the Step 5 item 15 last-mile re-check already force re-review when the
resolution commit advances HEAD — that machinery is **reused, not rebuilt**.

### D2 — The immutable annotated-tag architecture is rejected for this unit

PR #396's tag design was judged mechanically sound but is **not necessary** to
close G1–G3, and it was never groundable: it required a `workspace_id`, a
recorded ruleset ID, and a carrying-PR binding that have no source in this
repository (F6, F7). Adopting it would reintroduce exactly the unsatisfiable
inputs that failed review eleven times. **Rejected on minimality.**

### D3 — Residual crash-window recovery is split out, not folded in

One residual remains after D1: an agent could crash **between** merge
confirmation and the resolution commit. Handling that requires durable
cross-session recovery state — a genuinely separate design problem with its own
substrate question.

Per the minimality rule, this is **split into a separate deliberation** and is
**not** a dependency of the mandatory unit. The ordering fix is strictly better
than today's behaviour with or without it, so making it unshippable pending a
substrate decision would be unjustified. No evidence indicates the core
invariant is unsafe to ship alone: it removes a *deterministic, reproducible*
failure and introduces no new failure mode.

### D4 — Defect 1 remains out of scope

Dark-mode same-scope checkpoint auto-routing stays a separate open deliberation.
No lineage, cursor, locking, CAS, or auto-routing work appears in this unit.

### D5 — P-001 and closure completeness are not weakened

Checkpoint-resolution *publication* is evidence that a checkpoint landed. It is
**not** a substitute for post-merge release closure, and it does not alter
P-020 compaction status or shipment archival. The two remain separate records.

### D6 — Fix the tracked contracts here; propagate upstream as separate scope

F8 forces an explicit choice about where the fix lives.

**Chosen**: apply the fix to the **tracked** `.github/agents/*.md` contracts in
this repository, and capture upstream template propagation as a **separate,
explicitly recorded follow-up** outside this release unit.

Rationale:

- `.github/agents/*.md` is what the agents actually read at runtime and what
  this repository version-controls. Fixing it closes the defect **here and now**
  for every subsequent session in this workspace.
- The upstream template lives in a **different repository** (`autoharness`),
  which is outside both this session's role boundary and the operator's
  authorization (scoped to `softwaresalt/agent-engram`). Blocking a correct,
  in-scope, in-repo fix on a cross-repository change would be an unjustified
  coupling.
- The regeneration risk is **real but operator-initiated and detectable** —
  `autoharness tune` performs drift detection, so the divergence surfaces rather
  than silently vanishing.

**Rejected alternative**: vendoring the templates into this repository to make
them authoritative. That is a substantially larger architectural change than the
defect warrants and is squarely a YAGNI violation for a three-gap ordering fix.

**This is disclosed, not hidden.** RR-3 below records the residual, and the plan
carries an explicit task to document the divergence at the edit site so a future
regeneration conflict is legible rather than mysterious.

## Requirements

Each requirement names its actual source. No undefined inputs.

| ID | Requirement | Source |
|---|---|---|
| RQ-1 | A checkpoint resolution MUST be committed before the final reviewed HEAD of the pull request that carries it. | G1; F1 |
| RQ-2 | **Positive form.** A checkpoint resolution MUST land on `main` via the same carrying pull request that is subsequently merged. Committing a resolution to any branch that cannot deliver it to `main` through that PR — an already-merged branch, or a branch with no open PR — is PROHIBITED. | G2; PR #395 root cause; round-1 review (negative phrasing was satisfiable while reproducing the defect) |
| RQ-3 | Ship MUST resolve in-scope session checkpoints during Step 6 closure work, at a point whose **execution order** precedes the Step 6.0 item-4 push/PR-creation action. | F4 |
| RQ-5 | After the carrying PR merges, the agent MUST verify that each resolution it performed is present on **`origin/main`**, evaluated against `origin/main` explicitly rather than against the currently checked-out branch. | G3; round-1 review (working-tree read gave false success) |
| RQ-6 | A checkpoint that is out of scope per D1 (terminal pause class) MUST be recorded as an explicit, operator-visible residual and MUST NOT be silently treated as handled by this unit. | D1; RR-2 |
| RQ-7 | Resolution MUST use the official `backlogit checkpoint resolve` command, never a manual JSON edit or cherry-pick. | F2; PR #395 ("not a manual JSON edit, not a cherry-pick") |
| RQ-8 | Each edited contract site MUST carry an inline note that the file is generated and that the change must be propagated upstream. | F8; D6; RR-3 |
| RQ-9 | The added steps MUST degrade to a clean no-op when no checkpoints are active. `backlogit checkpoint list --status active` returns `{"checkpoints": null, "total": 0}` — **`null`, not `[]`** — so the null case MUST be handled explicitly and MUST NOT produce a halt. | Round-1 review; live command output verified this session |

**Retired**: RQ-4 (Stage symmetry) is withdrawn from this unit. Round-1 review
established that its premise — a Stage "staging PR" acting as the carrying HEAD —
is ungrounded: the Stage role boundary lists PR creation as forbidden, and Stage
has no Step-6/closure equivalent, so `before final reviewed HEAD` has no anchor
for Stage. Applying only the prohibition without a sanctioned resolution site
would leave Stage-owned checkpoints permanently unresolvable. The Stage-side
defect (F5) is real and is recorded as **RR-4**, deferred to separate scope.

Explicitly out of scope: tags, markers, rulesets, repository settings,
`workspace_id`, auto-routing, lineage, locking, CAS.

## Consequences

**Accepted cost.** Resolving before the final HEAD advances HEAD, which re-arms
§1.9 and P-018 and costs one additional review round on closure PRs. This is the
existing, intended behaviour of those gates (F6) — not a new burden.

**Residual risk (RR-1).** Crash between merge confirmation and the resolution
commit leaves a checkpoint active on `main`. Detection is unchanged from today:
the next session's fail-closed enumeration surfaces it and halts to the
operator. This is **no worse than current behaviour** and is the subject of D3's
separate deliberation.

**Residual risk (RR-2) — terminal pause class.** Out of scope per D1. These
checkpoints are created after their PR's final HEAD by construction. RQ-6
requires them to be recorded as explicit residuals so they are visible rather
than mistaken for handled. **This unit does not fix them**, and their present
behaviour (an active checkpoint on `main` triggering the next session's
fail-closed operator halt) is **unchanged by this unit** — neither improved nor
worsened. Fixing them is D3's separate deliberation.

**Residual risk (RR-3) — upstream template divergence.** Per F8/D6 the fix is
applied to generated-but-tracked contracts whose upstream template is not in this
repository. A future `autoharness install`/`tune` regeneration could revert it.
Mitigation: an in-file divergence note at each edit site (RQ-8) so the conflict
is legible, plus a separately captured upstream-propagation follow-up. This
residual is **accepted, disclosed, and does not block** the in-repo fix.

**Residual risk (RR-4) — Stage-side defect unfixed.** F5 established that
`_stage.agent.md` carries identical defective Session-end text. RQ-4 was retired
because its carrying-PR premise is ungrounded. The Stage exposure therefore
**remains open** after this unit and is deferred to separate scope alongside D3.
This is disclosed, not hidden.
