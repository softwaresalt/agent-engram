## Problem Frame

Shipment 142-S is halted before implementation. `.github/agents/_ship.agent.md`
has two rules that together block it:

* **Step 2, item 4** requires every task to carry `harness-ready`, meaning a
  compilable, failing test harness.
* **Step 3, item 2** builds the ready queue from `harness-ready` tasks only.

F55 (142.059-T) owns only `docs/troubleshooting.md` and was deliberately left
out of F00 test registration. Ship labeled it `harness-not-applicable` and
recorded three executable checks:

1. `backlogit docs lint --path docs`
2. Cross-check refusal codes against `src/errors/codes.rs`
3. Cross-check surfaces against the F54 matrix

The policy has no path that accepts this label.

A fix must not:

* mark docs `harness-ready` when they have no harness (a false claim)
* invent a test file outside F55's declared surface
* mutate the active 142-S manifest
* weaken P-002/P-004 for code tasks

## Research Findings

* The five code tasks, 142.054–142.058, have compiling RED harnesses. The F54
  harness needs a one-line re-verification after the 2026-09-24 acceptance
  amendment; see the CLI parity deliberation.
* `_ship.agent.md` already recognizes that documentation-only work is a real
  category. Around lines 564 and 587 it lets documentation-only PRs record that
  a full build does not apply. Only the Step 2 and Step 3 task gates lack an
  equivalent.
* `_ship.agent.md` is generated by autoharness. A durable fix belongs in the
  harness template channel (autoharness template plus auto-tune, or an
  operator-owned harness edit). Stage cannot edit agent or instruction files,
  and the fix is not application code.
* The compound library has no precedent for this case. The learnings search
  returned low confidence.
* Secondary ambiguity: Step 2, item 1 lists tasks in `queued` status, but all
  142-S tasks are `active` after claim. Step 3, item 1 already handles `active`
  tasks. The policy amendment should align the two steps.

## Options Evaluated

### Option 1: One-time scoped operator disposition for 142.059-T (recommended as the immediate unblock)

The operator records an explicit, audited Step 2 disposition covering exactly
142.059-T. It accepts the three recorded verification commands as that task's
gate, which Ship runs before closing the task. F55 stays last in dependency
order.

* **Pros:** fastest path, no manifest change, and no false label. Code-task
  gates are unchanged.
* **Cons:** this is an exception, not a policy fix, so it needs Option 2 to
  follow.
* **Effort:** low.

### Option 2: Harness-policy amendment adding a verification-gated docs disposition (recommended as the durable fix)

Add an explicit label and rule, for example `harness-verification-gated`. A
task qualifies only when all of these hold:

* It declares no code, test, or config surface.
* It records executable verification commands before implementation.
* Its verification is re-run as its completion gate.

Steps 2 and 3 would accept this label in place of `harness-ready` for such
tasks only. Apply the change through the autoharness template, then auto-tune
or an operator harness edit.

* **Pros:** fixes the root cause and is auditable.
* **Cons:** needs its own plan and review cycle. It is a harness change, so it
  must go through the template channel.
* **Effort:** medium.

### Option 3: Give F55 an executable doc-contract test

* **Cons:** F55 would own a test file, which changes its surface, its width,
  and its F00 registration. The width rule would force a split into a test task
  and a docs task, which is a 142-S manifest change.
* **Status:** rejected while 142-S is active.

### Option 4: Remove F55 from 142-S or pause the shipment

* **Cons:** changes the active manifest, and Ship owns shipment transitions.
* **Status:** rejected.

## Decision

**DECIDED 2026-09-24 (operator): Option 2, the durable harness-policy change.
Option 1 (a one-off waiver for 142.059-T) is NOT authorized.**

142.059-T (F55) stays `harness-not-applicable` and is not queue-eligible until
the amended harness is installed. Stage cannot edit agent, template, or policy
files. Ship cannot author the amendment as a 142-S task. The amendment goes
through the operator-owned harness template channel.

### Amendment Specification (handoff to the template channel)

This specification is the planning output for the operator or autoharness
maintainer.

1. **Label.** Add the canonical label `harness-verification-gated`. Ship's
   existing `harness-not-applicable` on 142.059-T is re-labeled by Ship once
   the amended harness is installed.
2. **Qualification.** A task qualifies only if all of the following are true.
   Ship checks them in Step 2 and halts if any fails.
   * (a) Every owned file is prose documentation (`docs/**/*.md`, top-level
     `*.md`). The task owns nothing under `src/`, `crates/`, `tests/`,
     `scripts/`, `.github/workflows/`, `Cargo.toml`, `*.ps1`, or `*.sh`.
   * (b) The task's verification section records at least one deterministic
     executable command before Step 2 completes. Each command must exit
     non-zero on failure, for example `backlogit docs lint --path docs`, or a
     scripted cross-check against `src/errors/codes.rs`.
   * (c) No executable test exercises the task's surface. If one exists, the
     task must use `harness-ready` against that test instead, as the parity
     docs unit does.
3. **P-002 amendment.** The precondition becomes: the task carries
   `harness-ready`, OR it carries `harness-verification-gated` and satisfies
   qualifications (a)–(c). Code, test, and config tasks are unchanged.
4. **P-004 amendment.** The rule for verification-gated tasks is:
   * The harness manifest records `Verification Commands: RECORDED` and
     `Surface Check: DOCS-ONLY CONFIRMED`, plus the baseline result of each
     command before implementation.
   * P-004's red-phase rule does not apply, and the manifest never claims it
     does.
5. **Step 2.** Item 4 accepts either label under the rule in point 3.
   * Align item 1 with Step 3 item 1: consider tasks in `queued` or `active`
     status.
6. **Step 3, item 2.** The ready queue accepts `harness-ready` OR qualified
   `harness-verification-gated` tasks.
7. **Step 4.** For a verification-gated task:
   * The recorded commands replace `harness_cmd` in build-feature and are the
     completion gate. Every command must exit 0.
   * The Step 4.3 lint, format, and `cargo dev-test` gates still run.
8. **Anti-loophole.** A task that carries the label while owning a
   non-prose path is a P-002 violation. Record it through P-005 and halt.
9. **Channel.** Upstream autoharness templates (`_ship.agent.md.tmpl`,
   `workflow-policies.md.tmpl`) are updated, then auto-tune regenerates this
   workspace's `.github/agents/_ship.agent.md` and
   `.github/policies/workflow-policies.md`. The operator reviews the diff. This
   is not a Ship release unit, so it does not compete with 142-S under P-001.
10. **Effect on 142-S.** No manifest change. Once the harness is installed,
    Ship re-labels F55. 142-S becomes resumable when the F54 harness fix
    (Ship owes it; see 035-D) is also done. The parity ordering is DECIDED
    (operator, 2026-09-24): Path S — 142-S ships first and parity is a later
    shipment, so parity does not gate 142-S.

**Original recommendation text (kept for provenance):** Option 1 now, then
Option 2 as the durable fix. The operator's decision above supersedes it.

Option 2 goes through the harness template channel rather than as a Ship
release unit, so it does not compete with 142-S under P-001. If the operator
would rather ship Option 2 as a Ship chore, it has to be sequenced after 142-S,
which makes Option 1 the only way to unblock 142-S sooner.

Stage cannot grant Option 1 itself. The disposition must be authored by the
operator. The suggested record is an operator comment on 142.059-T, plus an
instruction to Ship that names the task, the three commands, and the fact that
no other task is waived.

## Rejected Alternatives

* **Option 3:** changes the width and manifest of an active shipment.
* **Option 4:** mutates the active manifest.
* **Relabeling F55 `harness-ready`:** a false claim.

## Unresolved Questions

   backlogit currently has `pending`, `scaffolded`, `passing`, and `failing`.
2. Whether the amendment should be made upstream in the autoharness template
   (recommended) or only in this workspace.
3. Whether to align Step 2, item 1 (`queued`) with Step 3, item 1
   (`queued` + `active`).

## Risks and Mitigations

* **Risk:** the exception is reused as a loophole for code tasks.
  **Mitigation:** the disposition names exactly one task and requires that the
  task declare no code, test, or config surface.
* **Risk:** local harness edits are lost at the next autoharness regeneration.
  **Mitigation:** apply the fix upstream in the template.
