This page explains the labels you see in agent status reports and approval
requests. If an agent uses a label that is not listed here, ask it to add it.

## Maintenance rule

Agents (Orchestrator, Stage, and Ship) keep this page current:

* Add an entry whenever a report, plan, or approval request introduces a new
  label or acronym that an operator is expected to read.
* Update an entry when a process change alters what a label means.
* Keep plan-specific labels in their own section and name the plan they
  belong to. Move them to the history section once that work ships.
* Update `last_updated` in the frontmatter with every edit.

## Workflow and process terms

| Label | Meaning |
|---|---|
| **Stage / Ship / Orchestrator** | The three agents. Stage plans the work, Ship builds it, and the Orchestrator coordinates the two. |
| **-F / -S / -T / -ST** | Backlog item types: Feature, Shipment (a release), Task, and Subtask. For example, `142-S` is a release and `142.054-T` is a task. |
| **Stash** | The intake list of ideas and follow-ups (IDs such as `86F93068`). Stage turns stash entries into planned work. |
| **Harvest** | Stage turns a reviewed plan into real backlog tasks. Harvesting does not add those tasks to a release. |
| **PA-n** | "Pending Approval": a numbered decision that needs your explicit OK before an agent may act on it. |
| **D*n*-A, D*n*-B** | Design decision *n* in a planning document, and its options. Option A is usually the recommended one. |
| **P0 / P1 / P2 / P3** | Severity of a review finding. P0 and P1 block progress. P2 and P3 are non-blocking and are usually carried into task acceptance criteria. (In the 142-F landing sequence, "P0" is also the name of a step; see P0 (landing step).) |
| **PASS / ADVISORY / FAIL** | Plan-review outcomes. PASS means no significant findings. ADVISORY means only non-blocking (P2/P3) findings, so you decide whether to proceed. FAIL means at least one P0 or P1 finding. |
| **P-001, P-015, P-021, ...** | Numbered workflow policies, defined in `.github/policies/workflow-policies.md`. For example, P-001 allows only one release in progress at a time. |
| **AC** | Acceptance criteria: the conditions a task must meet before it counts as done. |
| **RED / GREEN** | Test-first terms. RED is a test written first that fails. GREEN means the code now makes it pass. |
| **`dag-root` (shipment label)** | Marks a release that has no release before it in the dependency order, so it can start without waiting on another one. The pre-claim topology check needs either this label or a real "blocks" link to an earlier release. Without one of them, it stops with `UNSEQUENCED_SHIPMENT`. |
| **Abandon (a shipment)** | Close a release permanently without shipping it. Nothing is deleted, and its tasks become free to join another release. It cannot be undone. |
| **Return-blocked** | A backlog command that takes one task out of an in-progress release and marks that task "blocked". |
| **ActionRisk (low / moderate / high / destructive)** | How risky a proposed step is. High means it cannot be undone. Destructive means it loses data. |
| **Parked branch** | A git branch that is kept, unchanged and unpushed, only so its commits can be copied (cherry-picked) into other branches later. |
| **Safe-close** | Formally closing a release that shipped only part of its feature, without marking the whole feature done. |
| **Checkpoint** | A saved agent state that allows a session to resume after a crash. |
| **Circuit breaker** | A stop rule that halts an agent after repeated failures (for example, three failed review attempts) until you decide what to do. |
| **ESCALATION_DEGRADED** | An agent tried to hand a problem to a stronger model but could not deliver it, so it stopped and is waiting for you instead. |
| **Dark mode** | An opt-in autonomous run, started only by an exact trigger phrase, with a bounded scope and pre-recorded approvals. |
| **Dogfooding** | Running this repository's own development tools on the engram version currently being built. |

## Technical terms

| Label | Meaning |
|---|---|
| **MCP** | Model Context Protocol: how Copilot talks to engram. |
| **CLI** | Command-line interface: the `engram` command. |
| **IPC** | Inter-process communication: how the CLI and the shim reach the running engram daemon. |
| **Daemon** | The background engram process that indexes the workspace and answers queries. |
| **Read server** | A daemon mode that serves queries from a prebuilt, sealed index (a "generation") instead of indexing in-process. |
| **Generation** | A published, sealed snapshot of the index that the read server serves. |
| **Preflight** | The self-check that confirms your locally built engram works before a launcher starts Copilot. |
| **Parity** | The requirement that the CLI and MCP behave the same for the same request. |
| **PR / CI** | Pull request, and continuous integration (automated checks on GitHub). |
