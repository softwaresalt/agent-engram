title: Indexing Resilience — SQLITE_BUSY Graceful Handling and Sync Timeout Prevention
updated_at: 2026-05-08T21:45:04.6565758-07:00
---

Harden the daemon against concurrent DB access failures during indexing. Two related bugs were discovered during the 028-S CLI test cycle:

1. **SQLITE_BUSY panic** (BUG-B): `stats`, `query_memory`, and `unified_search` tool handlers do not check `is_indexing()` before opening a DB connection. When indexing holds the write lock, read attempts hit CozoDB error code 5 (SQLITE_BUSY). The `.unwrap_or(0)` in `get_workspace_statistics` silently swallows the error, but other tools may panic or return confusing internal errors.

2. **Sync IPC timeout** (BUG-C): `sync_workspace` waits for the DB lock held by the indexing task, but the IPC request times out (30s) before indexing completes. The user gets a cryptic `IPC failure: IPC request timed out after 30000ms` with no indication that indexing is in progress.

Both bugs share the root cause domain: tools that access the DB do not uniformly handle the "indexing in progress" state. The fix pattern is consistent — add `is_indexing()` guards or return a fast `IndexInProgress` error so the caller can retry.
