## Description

Operator-approved release unit to cut **`v0.3.0-rc.1`** from `main` at `bdda5aac8e6326d646e3b30d3144e4349db770a9` for **dogfooding only**.

Latest public release is stable `v0.2.0` (2026-06-16); `main` is ~1,409 commits ahead. This RC exists to get a consumable, versioned artifact into dogfood hands without representing it as stable.

### Explicit non-goals (do not widen)

- Daemon readiness / Cozo cold-start remediation. Live dogfood verification on 2026-08-29 failed: `engram workspace-status` and indexed search timed out because the daemon did not reach Ready within 30s. Root cause is tracked by queued high-priority spike **002-SP** (~7.5 min cold open of a 135 MB Cozo database). Raising the readiness timeout is explicitly NOT an acceptable remediation and is NOT in this unit.
- MCP/RMCP modernization. Engram resolves `rmcp` 1.8.0 (upstream 3.1.4). Current VS Code Copilot uses MCP 2025-11-25; MCP 2026-07-28 support remains planned. Touch RMCP/MCP surfaces only if existing release mechanics require *metadata* changes.
- crates.io publication. `publish = false` in `Cargo.toml` and `release.toml` stays as-is. Distribution is GitHub Releases only.
- Any new broad feature implementation, refactor, or workflow redesign.

### Scope boundary with unrelated queue artifacts

`002-SP`, `128-F`, and `129-F` are unrelated. This feature **references** `002-SP` in release notes but must not modify, absorb, or reprioritize any of the three.

### Known release-mechanics risk discovered during staging

No `cliff.toml` / `[workspace.metadata.git-cliff]` config exists in the repository, yet `.github/workflows/release.yml` `changelog` job runs `git-cliff --latest --strip header` and falls back to the literal string `No changelog entries for this release.` on empty output. For a tag ~1,409 commits past `v0.2.0`, that job will either emit nothing usable or dump an unreadable wall of commits. Requirement: the published body must be curated. See plan Decision D2 for the bounded remediation and its fallback.

### Approval boundary (NON-NEGOTIABLE)

The operator approved **staging and building** the RC release unit. That approval does **not** bypass PR merge policy. Ship may prepare a release PR; Ship must **not** merge it, and must **not** create or push the `v0.3.0-rc.1` tag or publish the GitHub Release, without explicit operator approval at the relevant gate. `release.toml` sets `push = true`, so `cargo release --execute` would push the bump commit and tag directly to `origin` and bypass both PR review and `detect-direct-push.yml`. It is therefore prohibited for this unit (plan Decision D1).

## Goals

1. `Cargo.toml` / `Cargo.lock` carry `0.3.0-rc.1` with `publish = false` preserved, produced without any direct-to-`main` push.
2. A curated, human-readable `[0.3.0-rc.1]` changelog / release body covering meaningful change themes since `v0.2.0` — not a 1,409-commit dump.
3. Unambiguous prerelease labeling and disclaimer: dogfood/RC, not stable, known daemon-readiness / cold-start defect referencing `002-SP`, stable `v0.3.0` blocked until reliability acceptance gates pass.
4. Focused smoke gates pass on all three packaged release artifacts (`x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`, `aarch64-apple-darwin`) plus MCP stdio behavior, on top of the mandatory existing CI/Release quality gates.
5. Documented rollback/withdraw criteria and release observability signals: startup/readiness success rate, cold/warm latency, crash/stale-state, compatibility feedback.
6. Tag `v0.3.0-rc.1` validated against the Release workflow's `validate-tag` regex and prerelease expression; GitHub shows the release as **Pre-release** and leaves `v0.2.0` as **Latest**.
7. Every gate that merges, tags, or publishes is executed only after explicit operator approval.
