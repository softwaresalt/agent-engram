## Description

Write the operational contract for the RC dogfood window as a single doc (suggested: `docs/decisions/2026-08-29-v0.3.0-rc.1-rollback-and-observability.md`) that the release body links to.

### Part A — rollback / withdraw criteria

Define concrete, pre-agreed triggers for withdrawing the RC, so the decision is not relitigated under pressure. At minimum:

- **Data-integrity trigger** — any report of index or database corruption, or irreversible workspace state damage. Severity: immediate withdraw.
- **Regression trigger** — a capability that worked in `v0.2.0` is broken in the RC. Severity: withdraw or supersede with `rc.2`.
- **Startup trigger** — startup/readiness success rate falls below the agreed threshold across dogfood users on workspaces the RC is expected to handle.
- **Crash trigger** — repeated daemon crash or stale-state lock requiring manual intervention.
- **Security trigger** — any new `cargo audit` advisory affecting shipped code paths.

Also define the **withdraw mechanics**: because this is a prerelease on GitHub Releases with no crates.io publication (`publish = false`), withdrawal means marking the release as a draft or deleting it, plus a superseding `rc.2` and a note in `CHANGELOG.md`. Explicitly state that the `v0.2.0` stable release must remain untouched and remain **Latest** throughout.

### Part B — release observability signals

Define what is collected during the dogfood window and how:

1. **Startup / readiness success rate** — fraction of daemon starts that reach Ready within the readiness window, bucketed by database size. This is the headline signal given the known `002-SP` defect.
2. **Cold vs warm latency** — time-to-Ready on first open of a cold database vs. subsequent warm opens; report median and p95, and always alongside database size in MB. The `002-SP` baseline is ~7.5 min cold on 135 MB.
3. **Crash / stale-state signals** — daemon panics, abnormal exits, orphaned lock files, and stale IPC endpoints requiring manual cleanup.
4. **Compatibility feedback** — MCP client interop results, chiefly VS Code Copilot (MCP 2025-11-25) against engram's `rmcp` 1.8.0 stack; plus OS/arch coverage gaps, notably the absent `x86_64-apple-darwin` artifact.

For each signal, state the source (existing telemetry envelope / structured logs per `docs/log-observation-guide.md` / manual dogfood report) and the collection cadence. **Prefer existing instrumentation.** If a signal has no existing source, record it as a manual dogfood report — do **not** add new instrumentation code in this release unit.

### Part C — reliability acceptance gates for stable v0.3.0

State the exit criteria that unblock stable `v0.3.0`, so the block on stable is falsifiable rather than open-ended. These must be tied to `002-SP` remediation and must **not** be satisfiable by increasing the readiness timeout.

## Implementation Notes

- Keep thresholds explicit and numeric where possible; a criterion that cannot be evaluated is not a criterion.
- Reuse the existing telemetry envelope and indexing metrics shipped in `0.2.0` rather than proposing new counters.
- This doc is the artifact the operator will read when deciding whether to withdraw — optimize it for fast decision-making, not completeness.
- Estimated effort: ~1.5h.
