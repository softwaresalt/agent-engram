AUDIT RATIONALE (manual safe-close): 135-S closes via targeted manual safe-close
per operator-approved merge of PR #383 (`Merge approved`, approved HEAD
`64414ec99089fc6eb3b902525d60ac31f76afd11`, merge commit
`0cfffc0cf7220d8f643da28cd2025aff558b7d76`, merge method: merge commit via
`gh pr merge 383 --merge`). PR #383 implemented all four manifest items
(142.023-T, 142.024-T, 142.025-T, 142.026-T), each independently verified
`done` and already individually archived under `.backlogit/archive/` prior to
this shipment-record closure step.

Manual safe-close (not the `backlogit shipment ship` cascade operation) was
required for two independent reasons:

1. **P-015 protected-scope risk**: `142-F` is a shared-parent covering feature
   for 7 additional queued/future shipments (136-S through 142-S, dozens of
   remaining task/subtask items across a 59-unit roster) plus the
   already-archived 133-S and 134-S. `142-F` is not a manifest member of
   135-S and does not meet the P-015 fully-covered-root exception (it is far
   from fully covered by this 4-item manifest), so the cascade `shipment ship`
   path — which force-releases the covering feature and can
   requeue/detach unshipped descendant siblings — is prohibited for this
   shipment regardless of tool behavior.
2. **Tool timeout symptom (`backlogit shipment ship` did not complete within
   any observed window)**: `backlogit
   shipment ship 135-S --sha 0cfffc0cf7220d8f643da28cd2025aff558b7d76 ...`
   was attempted three times (v1.10.1-0.20260823032255). The command did not
   return in any of the three attempts (killed after ~4 min, ~3 min, and
   ~5.5 min respectively) with steadily climbing CPU
   time (observed up to ~211s of CPU across ~5.5 minutes wall time on the
   third attempt) and **zero WAL growth** (`.backlogit/backlogit.db-wal`
   remained at a fixed size throughout), establishing that the command
   exceeded all three observation windows with no persisted database-write
   progress. The root cause is unconfirmed (see the linked compound entry);
   a plausible but unproven hypothesis is an expensive/unbounded traversal
   of `142-F`'s large descendant tree during the command's "protected set"
   provenance proof. The generic
   `backlogit move 135-S --status shipped` path was also attempted and
   rejected outright by the CLI: `shipment must be shipped via ShipShipment,
   not a direct status update`. Six long-stale `backlogit mcp` server
   processes (dated 2026-09-01 through 2026-09-05, orphaned from prior
   sessions) were found holding the shared SQLite workspace database and were
   terminated as a precautionary unblock attempt; this did not resolve the
   symptom, ruling out lock contention as a contributing factor (though it
   does not by itself establish the true root cause). Each attempt was
   verified to have made **no persisted state
   change** (WAL size unchanged, `135-S` status unchanged, no archive file
   written) before being terminated by PID, so no partial/corrupt state was
   produced. This tool defect is stashed as a follow-up
   (see repository stash) for upstream investigation.

Only the four items explicitly enumerated in this shipment's manifest were
mutated (individually archived during routine task-completion bookkeeping
ahead of this closure step); `142-F` remains `active` and byte-for-byte
untouched (verified via pre-attempt snapshot comparison); no other `142.*`
item's `parent_id`, status, or shipment membership was altered by this
closure.

`archived_status: done` (rather than `shipped`) is deliberate, not an
oversight: it factually records that this record did not transit the
`active -> shipped` `ShipShipment` cascade (the CLI hard-rejected the
direct-to-`shipped` path, see tool defect above), and it matches the
identical, already-established manual-safe-close precedent for the
`archived_status: done` / manual-archive-file format on `133-S` and `134-S`
(`.backlogit/archive/133-S.md`, `.backlogit/archive/134-S.md`, both also
`archived_status: done`) — `134-S` shares the P-015 shared-covering-feature
safe-close reason (it does not record a tool hang), and `133-S` carries no
audit rationale text at all. The timeout symptom described above is specific
to `135-S`. Rewriting
it to `shipped` here alone would misrepresent the closure mechanism actually
used and break consistency with that precedent chain. On the raised
dependency-eligibility question for successors such as `137-S`: `135-S`
itself declares `dependencies: - 133-S`, and `135-S` was not blocked from
being created or claimed despite `133-S` carrying this identical
`archived_status: done` (135-S itself never transited to `shipped` either —
see the manual safe-close rationale above — so this example demonstrates
only creation/claim eligibility, not shipped-status propagation) — evidence
that eligibility for a dependent shipment is not gated solely by this
archived-record frontmatter field.
Whether `137-S`'s eligibility check needs independent verification (or
whether the manual-safe-close convention itself should evolve) is broader
than this closure artifact and is captured as a follow-up for Stage
triage rather than resolved unilaterally here.
