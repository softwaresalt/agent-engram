# query_graph Implementation — DSL Design and Execution Strategy

## Problem Frame

<!-- BEGIN:problem-frame -->
The `query_graph` MCP tool and CLI subcommand currently return `GraphQueryError::Invalid` (stub). The code graph stored in CozoDB contains symbol nodes (functions, classes, files) and edges (calls, references, contains, parent_of, depends_on). Users and agents need a way to query this graph beyond the existing `list_symbols`, `map_code`, and `impact_analysis` tools. The question is: what query DSL should `query_graph` support, and how should it execute against the CozoDB backend?
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
Option A: CozoScript passthrough — expose CozoDB's native Datalog query language directly. Minimal implementation effort but leaks storage internals and requires callers to know CozoScript syntax and relation names.

Option B: Simple structured query API — define a JSON-based query schema with predefined traversal patterns (e.g., find_callers, find_callees, shortest_path, transitive_deps). Limited but safe and easy to use from MCP clients.

Option C: Lightweight graph query DSL — define a small domain-specific query language (e.g., path expressions like `fn:main -calls-> fn:* -references-> class:*`) that compiles to CozoScript. More expressive than B, more user-friendly than A, but requires parser work.

Option D: Hybrid — structured queries (Option B) for common patterns plus raw CozoScript passthrough (Option A) for advanced use, behind a feature flag or explicit opt-in parameter.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option B: Simple structured query API. Rationale: (1) The existing tools (list_symbols, map_code, impact_analysis) already cover many traversal needs — query_graph should complement them with multi-hop and path queries rather than reimplementing them. (2) A structured API is safest for MCP clients (agents) that construct queries programmatically. (3) CozoScript passthrough (Option A/D) would expose internal schema and create a maintenance burden if relations change. (4) A custom DSL (Option C) is over-engineered for the current use case — it can always be added later if structured queries prove insufficient. Start with a small set of traversal operations: find_path (shortest path between two symbols), transitive_closure (all reachable symbols from a starting point via specified edge types), and neighborhood (N-hop ego graph around a symbol).
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. Should query_graph results include full node metadata or just IDs + names? Full metadata is more useful but heavier. 2. Should there be a result size limit to prevent runaway queries on large graphs? 3. How should backlog edges (parent_of, depends_on from hydration) interact with code-graph edges? Same query namespace or separate? 4. What is the error handling for queries that reference non-existent symbols?
<!-- END:open-questions -->
