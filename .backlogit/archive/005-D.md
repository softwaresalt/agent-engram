# Documentation overhaul and focused docs information architecture refresh

## Problem Frame

<!-- BEGIN:problem-frame -->
The current documentation set does not match the codebase well enough to serve as a reliable entry point for users or agents. The highest-visibility problem is the root README: it still presents Engram primarily as an HTTP/SSE server backed by SurrealDB, while the current codebase centers on a shim/daemon CLI experience with IPC transport, CozoDB storage, richer CLI parity commands, and newer observability/report surfaces. Drift is spread across README.md, docs/configuration.md, docs/mcp-tool-reference.md, docs/troubleshooting.md, and smaller operational guides. The work needs a deliberate docs refresh that turns the root README into a concise brochure with basic installation only, then moves detail into focused docs pages for architecture, usage, configuration, tools, workflows, and operations.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
- Option A: Patch the obvious inaccuracies in place and keep the current documentation structure
- Option B: Rewrite only README and quickstart, defer the rest of the docs until later
- Option C: Treat this as a documentation information-architecture refresh: audit drift, reshape README into a brochure, and reorganize detailed material into focused docs pages with explicit cross-links and clear ownership of concepts
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Choose Option C. The docs problem is structural, not only textual. The implementation should begin with a drift audit against the current CLI and daemon architecture, then rewrite README.md as a short product overview plus basic install path, and redistribute detail across focused docs pages. Existing deep references such as architecture, configuration, tool reference, troubleshooting, and log-observation material should be retained or rewritten where useful, but the final structure must read as a coherent docs set instead of a collection of legacy pages.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
- Which existing docs should be rewritten in place versus replaced by new focused pages such as docs/usage.md, docs/workflows.md, or docs/operations.md?
- Should the refresh normalize path/casing inconsistencies around architecture doc references so docs/architecture.md becomes the clear canonical path everywhere?
- How much of the current tool-by-tool detail belongs in the main docs set versus deeper reference pages?
- What minimal installation story belongs in README without recreating the current wall-of-text problem?
<!-- END:open-questions -->

## Notes

<!-- BEGIN:notes -->
Audit evidence gathered during staging: README.md still describes localhost HTTP/SSE + SurrealDB and curl-based /sse and /mcp usage; docs/configuration.md still treats ENGRAM_PORT and HTTP/SSE as primary runtime concepts and references rollback_to_event; docs/mcp-tool-reference.md still states all tools are called over HTTP/SSE; docs/troubleshooting.md still uses /rpc and /sse as primary diagnostics. Current code and CLI surfaces in src/bin/engram.rs instead center on shim/daemon, install/update/reinstall/uninstall, bind, sync/index with direct mode, symbols/map-code/impact, query-graph, stats, health, branch-metrics, and report subcommands. Cargo.toml shows CozoDB as the active embedded backend while legacy-sse is feature-gated.
