# Engram evals/gates scope — first-slice split & duplicate check

## Problem Frame

<!-- BEGIN:problem-frame -->
Stash B87680AB asks engram to implement its share of the autoharness "Deterministic Gates, Telemetry & Evaluation Engine" design (docs/design-docs/autoharness-evals-gates-design.md) as the Structural Authority + Telemetry sink. Engram-scoped work is four distinct workstreams: Phase 1a `engram verify <path>` structural AST/YAML-frontmatter linter CLI (non-zero exit blocks autoharness pre_task_completion); Phase 1b reactive sync daemon that syncs valid, mutated markdown into CozoDB nodes; Phase 2c ExecutionEpoch CozoDB relational schema; Phase 2d JSONL telemetry ingestion linking epochs to Task and Code nodes. This spans linter, daemon, schema, and ingestion domains — far larger than a single 2-hour task/shipment. Before planning we must (1) confirm the work is not already implemented, (2) pick a defensible lowest-risk first slice, and (3) ground the plan on real engram modules.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
A) Single shipment covering all four phases — REJECTED: violates 2-Hour Rule and Width Isolation; Phase 1b (daemon event loop) and Phase 2c (CozoDB schema evolution) carry materially higher blast radius than the self-contained Phase 1a CLI.
B) First slice = Phase 1a `engram verify` linter CLI only (local, no-daemon, no schema change), defer 1b/2c/2d as dependency-linked follow-on tasks under one umbrella feature — CHOSEN. Phase 1a is the critical unblocker for the autoharness gate and has the lowest dependency risk.
C) First slice = Phase 2c schema first — REJECTED: schema evolution is higher blast radius and delivers no immediate gate value; Phase 1a must land first.
Architecture sub-choice for the linter: (i) extend the existing ADVISORY markdown lint in src/services/parsing/markdown.rs (lint_summary/suggestions) vs (ii) a new deterministic services::verify composing parsing::frontmatter::parse + parsing::markdown. CHOSEN (ii): advisory suggestions are non-binary; Phase 1a requires a deterministic pass/fail exit-code contract.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
One umbrella feature for all four phases. FIRST queued shipment covers Phase 1a only, decomposed into three dependency-ordered, width-isolated, test-first tasks: (T1) verify linter core service + result model; (T2) `engram verify <path>` CLI subcommand with exit-code/stderr contract; (T3) cross-platform path normalization + subprocess integration test. Defer Phase 1b (T4), Phase 2c (T5), Phase 2d (T6) as queued tasks under the same feature with explicit dependency links (T4 depends on T1; T6 depends on T5). Reuse real code paths: bin/engram.rs clap Command enum (register Verify like the local `manifest` command → run_verify -> i32), src/services/parsing/frontmatter.rs::parse, src/services/parsing/markdown.rs, src/services/ingestion.rs content path, and the established forward-slash path convention (`.replace('\\','/')`).
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1) Frontmatter policy: verify treats PRESENT-but-malformed YAML as a hard failure (closes the silent-None gap in frontmatter::parse); ABSENT frontmatter is a pass in Phase 1a unless a required-frontmatter doc class is configured (deferred). 2) Verify accepts per-file paths only in Phase 1a (matches design's `engram verify {file_path}`); glob/dir support deferred. 3) Non-markdown files: Phase 1a no-op pass (only markdown is graph-ingested). 4) Shared path-normalization utility vs the current ad-hoc `.replace('\\','/')` convention repeated across ~15 files — deferred to avoid width creep; Phase 1a reuses the convention. 5) Design Open Q on infinite correction loops and pre-execution sizing is autoharness/backlogit-side, out of engram scope.
<!-- END:open-questions -->
