Produce the human-readable release body for `v0.3.0-rc.1`, covering both the curated change summary and the prerelease disclaimer. These are one task because they ship as one artifact (the release body / CHANGELOG section).

### Part A — curated changelog section

Also update the `[Unreleased]`/comparison link footer consistent with the `release.toml` `pre-release-replacements` link conventions.

### Part B — RC disclaimer block (mandatory, verbatim intent)

The section must open with a clearly delimited disclaimer stating all of:

- This is a **release candidate for dogfooding only**. It is **not** a stable release and carries no stability or compatibility guarantee.
- **Known defect:** daemon readiness / cold start. Verified 2026-08-29: `engram workspace-status` and indexed search timed out because the daemon did not reach Ready within 30 seconds. On a 135 MB Cozo database, cold open has been measured at roughly 7.5 minutes.
- Root-cause investigation is tracked by spike **`002-SP`** (link/reference it). Raising the readiness timeout is explicitly **not** an accepted remediation.
- **Stable `v0.3.0` is blocked** until the reliability acceptance gates pass.
- Compatibility note: engram resolves `rmcp` 1.8.0; MCP protocol modernization (MCP 2026-07-28) is planned and not in this RC.
- Pointer to the rollback/withdraw criteria and observability doc produced by the sibling task.

### Part C — Decision D2: make the workflow publish this body

Staging found **no** `cliff.toml` and no `[workspace.metadata.git-cliff]` in `Cargo.toml`, yet `.github/workflows/release.yml` `changelog` job runs `git-cliff --latest --strip header` and publishes its stdout as the release body. Preferred order, stop at the first that works:

1. **Dry-run first.** Run `git-cliff --latest --strip header` locally against a local `v0.3.0-rc.1` tag and inspect the output. If it already yields a curated, readable body, no workflow change is needed.
2. If it yields nothing / the `No changelog entries for this release.` fallback / an unreadable commit wall, make the **minimal** change confined to the `changelog` job: source the body from the curated `CHANGELOG.md` `[0.3.0-rc.1]` section instead of raw `git-cliff` output.
3. Adding a `cliff.toml` is acceptable **only** if it is the smaller change and still yields a curated body. Do not redesign the release workflow.

Any workflow edit must keep existing security conventions: SHA-pinned actions, `permissions: contents: read` at workflow level with `contents: write` only on the `release` job, and `persist-credentials: false` on checkouts.
