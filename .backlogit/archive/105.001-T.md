PR #297 Copilot thread, src/tools/lifecycle.rs:255 (cancel) / :280 (DB-connect-failure). clear_all_pending_sync is a whole-queue store(0) wipe, not generation-scoped. set_workspace installs the new snapshot BEFORE cancelling the old hydration; in that cancel race window a sync against the NEW binding can fail the still-held indexing lock, publish_pending_sync its pending+companion bits (write.rs:287), then have them erased by the old generation's clear -- silently dropping the caller's explicit --revalidate-code-graph / --backfill-python-canonical intent until the new generation's own re-scan re-establishes edges. Fix: generation ownership on the pending queue (ownership tag) or a cancellation hand-off of requests published after the new binding, instead of an unconditional wipe. Narrow race; recoverable (new-gen full index still yields correct edges).

<!-- BEGIN:acceptance-criteria -->
- AC1 (RED FIRST, MUST FAIL pre-fix): a deterministic lifecycle test installs a NEW-generation snapshot, publishes pending + both companion bits (revalidate + backfill_python) against the new binding, then drives the OLD generation's cancel path clear_all_pending_sync (lifecycle.rs:255) -- and a second variant via the DB-connect-failure path (:280) -- and asserts the NEW-generation bits SURVIVE. Fails today (whole-queue store(0) wipe erases them). No wall-clock sleeps; use existing state hooks.
- AC2 (GREEN): the clear zeroes ONLY the owning generation's pending + companion bits; a newer-generation caller's explicit --revalidate-code-graph / --backfill-python-canonical intent survives an older generation's clear.
- AC3: preserve the 104-F publish-order atomicity invariant (write.rs:280-287) -- a concurrent drain never observes pending_sync==true with a stale/missing companion bit.
- AC4: no false heavy sync -- an old-generation stale companion bit never leaks into a new-generation routine sync.
<!-- END:acceptance-criteria -->
