## Description

Move the release-unit version surfaces from `0.2.0` to `0.3.0-rc.1`.

Confirmed surfaces (staging survey found no other hardcoded `0.2.0` in `README.md`, `start.ps1`, `start.sh`, or `scripts/`):

1. `Cargo.toml` → `[package] version = "0.3.0-rc.1"`. Leave `publish = false`, `edition`, and `rust-version` untouched.
2. `Cargo.lock` → the `name = "engram"` entry (currently line ~1047-1048) must resolve to `0.3.0-rc.1`. Regenerate via a lock-only refresh (e.g. `cargo check --locked` will fail; use `cargo update -p engram --precise` semantics or a plain `cargo metadata`/`cargo check` that rewrites the lock, then re-verify `--locked` passes).
3. No change to `crates/powerbi-tmdl-parser` version — it is a workspace member with an independent version and is not part of this release unit.

### Decision D1 — cargo-release execute path is PROHIBITED here

`release.toml` sets `push = true`, `push-remote = "origin"`, and `allow-branch = ["main"]`. Running `cargo release 0.3.0-rc.1 --execute` would create the bump commit AND the `v0.3.0-rc.1` tag and push both straight to `origin/main`, bypassing PR review and tripping `.github/workflows/detect-direct-push.yml`.

Therefore:
- Do the bump as a normal edit on a release branch, or run cargo-release strictly in dry-run / `--no-push --no-tag --no-confirm` mode to reuse its replacement logic locally.
- Tag creation is deferred to the operator-gated task `T-tag` and never happens in this task.
- Do not modify `release.toml` to work around this; record the deviation in the release PR description instead.
