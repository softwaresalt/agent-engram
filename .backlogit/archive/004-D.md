# Markdown structure-aware chunking for embeddings and graph search

## Problem Frame

<!-- BEGIN:problem-frame -->
We need markdown linting plus structure-aware chunking so markdown content can be embedded, searched, and linked below the whole-file level. Prior analysis says the primary blast radius is search, ingestion, and content schema, with markdown parsing as a supporting surface rather than the center of gravity. The deliberation must also evaluate whether a smaller model such as Haiku should work with a markdown linter to suggest or inject missing headings and subheadings so chunk boundaries become more stable and graph-linkable.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
- Option A: parser-first chunk extraction with minimal schema change; fastest path but weak retrieval fidelity and limited linkage\n- Option B: ingestion/schema-first chunk model plus search integration, with lint/normalization as a separate follow-on capability\n- Option C: full structure-aware pipeline: chunk model + ingestion + search integration + markdown linter/normalizer, with optional graph linkage and explicit evaluation of Haiku-assisted heading proposals
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Keep the work framed as a feature-level deliberation centered on search/ingestion/schema evolution, not a parser-only enhancement. Preserve a likely implementation split of (1) chunk model plus ingestion, (2) search integration, (3) markdown linter/normalizer, and (4) optional graph linkage. Treat Haiku-plus-linter heading injection as a design decision to be evaluated with guardrails, especially advisory versus automatic insertion.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
- Should heading injection remain advisory-only, or can the system safely auto-apply linter/model suggestions?\n- What provenance, diff visibility, and rollback trail are required if headings are injected automatically?\n- Should chunk graph linkage be mandatory for initial retrieval quality, or deferred behind search integration?\n- What chunk identity and schema fields are needed so chunks remain stable across file edits and re-indexing?\n- How should lint failures, missing headings, and synthetic headings affect ingestion and search ranking?
<!-- END:open-questions -->

## Notes

<!-- BEGIN:notes -->
Affected areas from prior investigation: (1) markdown structure extraction in src/services/parsing/markdown.rs and tests/integration/markdown_indexing_test.rs; (2) content ingestion in src/services/ingestion.rs where markdown is currently full-file ContentRecords with MAX_EMBED_CHARS = 4096; (3) content schema/persistence in src/models/content.rs and src/db/cozo_queries.rs where ContentRecord is keyed by file_path and lacks chunk metadata; (4) semantic retrieval in src/tools/read.rs, src/services/search.rs, and src/db/cozo_queries.rs where query_memory and unified_search are whole-file on the content side today; (5) graph-assisted retrieval in src/tools/read.rs and src/db/cozo_queries.rs where impact_analysis already supports hybrid structural plus semantic ranking via concept but markdown chunks would need graph linkage or chunk-to-symbol association; (6) reusable parser and metadata surfaces in src/services/parsing/frontmatter.rs and src/services/backlog_indexer.rs. Highest blast radius is the content-record model and retrieval pipeline.
<!-- END:notes -->
