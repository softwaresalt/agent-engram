Source stash FF7DE872; deliberation 014-D; plan docs/exec-plans/2026-07-27-ff7de872-same-file-shadowing-fail-closed-plan.md (reviewed, hardened). find_function_id (src/services/code_graph.rs:2988) resolves a direct-edge callee target by NAME ONLY via first-match .find(). When one file declares >1 top-level def of the same name (Python last-def-wins shadowing; Rust same-name in different inline `mod` blocks per file), the two direct-edge minting sites — index path (~code_graph.rs:1644-1645) and incremental-sync path (~2522-2523) — bind a bare call to the FIRST (shadowed/earlier) def instead of the effective target, minting a WRONG call edge (013-D no-false-edge / 082-F target-correctness violation). Newly EXPOSED (not introduced) by Python 094-F; the SHARED find_function_id consumer also affects Rust same-name-in-different-inline-modules-per-file. INDEPENDENT of FE8B3B2D/096-F: same-file bare calls take the DIRECT-edge path BEFORE any canonical/singleton post-pass, so 096-F's canonical resolver cannot fix this (it fails closed on duplicate canonical_path, never last-wins). Chosen direction (Option A, deliberation 014-D): fail-closed on same-file same-name ambiguity, language-agnostic — an additive ambiguity-aware resolver used ONLY at the direct-edge callee (and caller) resolution sites, leaving find_function_id byte-identical for its other 6 call sites. Option B (source-order/last-wins) REJECTED for v1 as unsound for Rust module-per-file.
