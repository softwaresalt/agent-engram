M4+Q2+R1: existing indexes will NOT acquire Python canonical EDGES through normal incremental indexing. Full-index and sync skip files whose content hash is unchanged (code_graph.rs:590-599 and :1252-1263), force defaults to false, and the canonical call post-pass runs on the full-index path ONLY (code_graph.rs:985-992). Q2: a version bump also fires on startup auto-SYNC, but sync re-extracts + clears prior resolved edges/staging then EXITS WITHOUT running the post-pass -- leaving staged calls UNRESOLVED until a later full index (a regression window). Re-extraction alone is insufficient. R1: do NOT mix the extraction version into file_node.content_hash -- retrieval_eval::is_index_stale (retrieval_eval.rs:717-718) compares content_hash BYTE-FOR-BYTE against the raw source SHA (source_content_hash, 699-700) and the indexer writes content_hash as that raw SHA (cozo_queries.rs:609 / schema.rs:573); mixing would break staleness detection. Instead track a PYTHON_CANONICAL_EXTRACTION_VERSION constant in a SEPARATE index-state marker -- persisted as a version-valued key in the existing durable schema_meta { key => value } relation (src/db/cozo_backend/schema.rs), read/written via the same durable get/set pattern the calls_resolution_rolled_back marker uses (schema_meta_flag_set / set_schema_meta_flag, schema.rs:275/307, generalized to store/compare a version value instead of a boolean "true"; relation created by CREATE_SCHEMA_META, schema.rs:876). (C14-3 SPLIT: this version-valued schema_meta get/set SEAM is OWNED by 096.013-T (T7-seam, DB/schema domain); T7 depends_on and CONSUMES it, retaining the indexing/rollout backfill logic in code_graph.rs.) Do NOT fold the version into any content hash (a version-fingerprinted hash would break the byte-for-byte content_hash staleness contract, R1). On a version mismatch, re-extract the affected .py files AND run the full canonical resolution pass in the SAME step (escalate to the full-index path, which runs the post-pass, or invoke the post-pass from sync) so resolved edges are restored in ONE operation, never left staged-but-unresolved; then persist the new version. C12-5 ENFORCEABLE ROLLOUT GATE: this backfill runs ONLY under an EXPLICIT opt-in -- the `engram index --backfill-python-canonical` CLI flag (C15-4: matches engram's boolean `--force`/`--full`/`--direct` index/sync convention -- indexing.rs:10-101, plumbed as a `force_params`-style JSON param across the index_workspace/sync_workspace boundary; env/activation vars are not used in engram, a cargo feature is rejected as it would require a recompile; the flag is read as a `backfill_python_canonical` param in code_graph.rs exactly like `force`); routine startup auto-SYNC DEFERS the backfill when the gate is absent (no marker advance, no re-extraction, no edge churn -- a no-op fast-path that logs a pending gated backfill), so the strict-safety operator-approval requirement is ENFORCED IN CODE, not merely documented. C7-3 PARTIAL-FAILURE GATE: persist the new marker ONLY on a fully-successful pass -- sync records per-file read/parse failures in SyncResult.errors and CONTINUES (code_graph.rs:1215-1221), so persisting the new version after a PARTIAL run makes the next sync see a current version and hash-skip the failed unchanged files INDEFINITELY (stale-forever hole; their Python canonical edges never backfill). The upgrade gate must KEEP THE OLD extraction-version marker whenever the pass had ANY per-file failure (non-empty errors for the affected .py set) so migration retries on the next sync; the new version persists only after every affected file AND the resolution pass succeed; when the outcome is uncertain, keep the old marker (fail closed toward retry). content_hash stays the raw source SHA. Documented fallback: a one-shot forced index --force. Replace the earlier 'no migration' claim with this real, single-step backfill trigger. TDD RED->GREEN. Domain: code.
