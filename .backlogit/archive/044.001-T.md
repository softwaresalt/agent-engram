## Add is_indexing() Guards to Read-Only Tool Handlers

## Problem

Several read-only tool handlers open a DB connection without checking whether indexing is in progress. When the indexing task holds the CozoDB write lock, concurrent reads hit SQLITE_BUSY (error code 5). Some handlers swallow the error via `.unwrap_or(0)`, others may panic or return confusing internal errors.

**Affected handlers** (in `src/tools/read.rs`):
- `get_workspace_statistics` (line ~85) — uses `.unwrap_or(0)` which silently returns zeros
- `query_memory` (line ~137) — no guard, will hit SQLITE_BUSY on `connect_db()`
- `unified_search` (line ~453) — no guard, will hit SQLITE_BUSY on search queries

**Already guarded** (no changes needed):
- `map_code` (line ~217) — has `is_indexing()` → `IndexInProgress` guard
- `list_symbols` (line ~366) — has guard
- `impact_analysis` (line ~683) — has guard
- `flush_state` (write.rs line ~26) — has guard

## Fix

Add `if state.is_indexing() { return Err(EngramError::CodeGraph(CodeGraphError::IndexInProgress)); }` to each unguarded handler, matching the pattern used by `map_code`, `list_symbols`, and `impact_analysis`.

Also audit remaining handlers in `read.rs` for the same gap:
- `get_health_report` (line ~785)
- `get_branch_metrics` (line ~862)
- `get_token_savings_report` (line ~917)
- `query_graph` (line ~978)
- `query_changes` (line ~1031)
- `get_evaluation_report` (line ~1141)
- `get_mutable_script_retry_metrics` (line ~1183)

## Acceptance Criteria

- All DB-accessing tool handlers in `read.rs` check `is_indexing()` before opening a connection
- Each guarded handler returns `CodeGraphError::IndexInProgress` (not silent zeros or panics)
- Contract tests verify that each affected tool returns the correct error code during indexing
- `cargo test` passes
- `cargo clippy -- -D warnings -D clippy::pedantic` clean

## Scope

- `src/tools/read.rs` — add guards to unprotected handlers
- `tests/contract/` — add or extend contract tests for IndexInProgress responses
