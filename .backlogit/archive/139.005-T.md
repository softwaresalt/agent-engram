## Description

Execute the tag and publish sequence for `v0.3.0-rc.1` under a hard operator-approval boundary.

### Approval boundary (NON-NEGOTIABLE)

The operator approved **staging and building** this RC release unit. That is **not** approval to bypass PR merge policy. Three distinct gates, each requiring a fresh explicit operator go:

| Gate | Ship may do without approval | Ship MUST NOT do without approval |
|---|---|---|
| **G1 — PR prepared** | Create the release branch, commit the bump + notes, open the PR, drive CI green, respond to review | Merge the PR |
| **G2 — Merge** | — | Merge to `main` |
| **G3 — Tag & publish** | — | Create or push the `v0.3.0-rc.1` tag; publish or edit the GitHub Release |

If the operator is unavailable at G2 or G3, **stop and leave the PR open**. Do not self-approve. Do not run `cargo release --execute` (`release.toml` has `push = true` + `allow-branch = ["main"]`, which would push commit and tag straight to `origin` and trip `.github/workflows/detect-direct-push.yml`).

### Pre-tag static verification (do this at G1, before any tag exists)

Verify by inspection that `v0.3.0-rc.1` will behave correctly in `.github/workflows/release.yml`:

1. **Trigger glob** `v[0-9]*.[0-9]*.[0-9]*` — confirm `v0.3.0-rc.1` matches (`-rc.1` is absorbed by the trailing `*`).
2. **`validate-tag` regex** `^v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.-]+)?(\+[0-9A-Za-z.-]+)?$` — confirm the `-rc.1` prerelease segment is accepted.
3. **Prerelease expression** on the `release` job: `contains(github.ref_name, '-pre') || contains(..., '-alpha') || contains(..., '-beta') || contains(..., '-rc')`. Confirm `v0.3.0-rc.1` contains `-rc`, so `prerelease` evaluates **true**.
4. Confirm `draft: false` and `generate_release_notes: false` — meaning the body comes entirely from the `changelog` job output, which is why task `139.002-T` must land first.
5. Confirm `fail_on_unmatched_files: true` and the `fail-fast: true` build matrix, i.e. a partial platform failure aborts publish rather than shipping an incomplete release.

### Post-publish verification (at G3, after the workflow completes)

1. GitHub Releases page shows `v0.3.0-rc.1` with the **Pre-release** badge.
2. **`v0.2.0` is still marked Latest.** This is the critical assertion — the operator decision is that nothing may represent the RC as stable.
3. All three archives are attached: `engram-v0.3.0-rc.1-x86_64-unknown-linux-gnu.tar.gz`, `engram-v0.3.0-rc.1-x86_64-pc-windows-msvc.zip`, `engram-v0.3.0-rc.1-aarch64-apple-darwin.tar.gz`.
4. The published body contains the curated notes and the RC disclaimer with the `002-SP` reference.
5. If GitHub incorrectly marks the RC as Latest, immediately re-mark `v0.2.0` as Latest and flag the RC as prerelease; record the discrepancy as a defect.

## Implementation Notes

- Tag from the merge commit on `main`, not from the release branch head.
- The Release workflow's `concurrency` group is `release-${{ github.ref }}` with `cancel-in-progress: false` — do not push the tag twice; a mistaken tag must be deleted and the release cleaned up before retrying, which is itself a destructive operation requiring operator approval.
- Because `generate_release_notes: false`, an empty `changelog` job output publishes an empty body. Confirm the changelog job output is non-empty in the run log **before** declaring publish successful.
- Estimated effort: ~1.5h of active work, plus operator wait time at G2/G3 which is not counted against the 2-hour rule.
