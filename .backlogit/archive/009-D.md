# Investigate Jupyter notebook source support

## Problem Frame

<!-- BEGIN:problem-frame -->
Decide whether `.ipynb` should enter engram as a JSON-backed container source and, if so, define the smallest viable source model for notebook metadata, markdown cells, and mixed-language code cells without yet committing to full implementation scope.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
- Defer notebook support entirely and document notebooks as unsupported
- Index notebooks as markdown-only documents and ignore code cells
- Treat notebooks as a dedicated JSON-backed container source with per-cell extraction for search and memory, with graph work staged later
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Choose the dedicated container-source path and record the bounded spike evidence in `docs/decisions/2026-05-22-jupyter-notebook-source-support-spike.md`.

The spike resolves the previously vague blocker:

- source model: one physical `.ipynb` source with notebook-level plus per-cell derived `ContentRecord` rows
- language precedence: recognized magic > `language_info.name` > `kernelspec.language` > `unknown`
- explicit v1 non-goals: outputs, execution counts, rich display payloads, arbitrary magic parsing, code-graph symbol extraction, and notebook graph edges
- fixture minimum: baseline Python/markdown, SQL magic, Scala magic, SparkR magic, and metadata-fallback notebooks

The stash has now been promoted into parent feature `063-F`.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
- Should the first shipped implementation stop at search/memory, or should it also add notebook-specific graph nodes and edges in the same feature after planning?
- Should v1 persist a notebook-summary record as `record_kind = file` or introduce an explicit notebook-specific record kind?
- Should the magic whitelist include `%python`-style line magics in addition to cell magics, or stay cell-magic-only in the first implementation slice?
<!-- END:open-questions -->

## Notes

<!-- BEGIN:notes -->
Repo evidence now points to a concrete path instead of an abstract investigation:

- `ContentRecord` already supports multiple retrieval units per file, which fits cell-level notebook extraction
- dedicated content-type dispatch already exists for `backlog` and `powerbi`, so a dedicated `notebook` path fits the current architecture
- `.ipynb` does not fit the code-graph extension-based language mapper, so notebook support should not be forced through the code parser path
- local repo search found no current notebook fixtures or notebook-specific ingestion logic beyond this deliberation chain

Harvest outcome for this pass: **parent feature harvested (`063-F`)**.

Not yet Ship-ready: Stage still needs an implementation plan, plan review, child task harvest, and shipment assembly before Ship has authoritative execution input.
