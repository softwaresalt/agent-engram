## Description

Define a **narrow** acceptance checklist for the RC and run it. This is a verification artifact plus at most a small helper script — explicitly not a new test framework, not a new workflow, not a new feature.

### Tier 1 — mandatory existing gates (must be green, do not modify)

These already exist and are non-negotiable for the RC:

- `Release` workflow `validate-tag` job.
- `Release` workflow `test` job (Quality Gates): `cargo fmt --all -- --check`; `cargo clippy --locked --no-default-features --features cozo-backend,embeddings --all-targets -- -D warnings -D clippy::pedantic`; `cargo test --locked --no-default-features --features cozo-backend,embeddings --all-targets`.
- `CI` workflow on the release PR: fmt, clippy, test, **oracle independence guard**, **cargo audit**, and the `start-launcher-windows` PowerShell launcher contract job.
- `Release` workflow `build` matrix with `fail-fast: true` across `x86_64-unknown-linux-gnu` (ubuntu-24.04), `x86_64-pc-windows-msvc` (windows-latest), `aarch64-apple-darwin` (macos-latest).

### Tier 2 — RC-specific packaged-artifact smoke

For each of the three published archives, unpack and verify:

1. Archive contains `engram` binary (`engram.exe` on Windows), `README.md`, `LICENSE`.
2. Binary is executable and `engram --version` reports **`0.3.0-rc.1`** (this is the end-to-end proof the version bump reached the shipped artifact).
3. `engram --help` exits 0.

### Tier 3 — MCP stdio smoke

On at least the Linux and Windows artifacts, drive the MCP stdio transport directly:

1. Launch the MCP stdio server, send a JSON-RPC `initialize` request, and assert a well-formed `initialize` result including `serverInfo` and the advertised `protocolVersion`.
2. Send `tools/list` and assert a non-empty tool array is returned.
3. Assert clean shutdown on stdin close (no hang, no panic, non-negative exit).
4. **Record** the advertised MCP protocol version in the RC verification record. Engram resolves `rmcp` 1.8.0; current VS Code Copilot uses MCP 2025-11-25. If the advertised version is not compatible, that is a **finding to record, not to fix in this unit** — raise it as a new stash entry.

### Tier 4 — known-defect boundary

Do **not** gate the RC on daemon readiness. `engram workspace-status` and indexed search are known to time out (30s readiness window; ~7.5 min cold open on a 135 MB Cozo DB, `002-SP`). Tier 2/3 must therefore avoid any check that requires the daemon to reach Ready against a large existing database. If a readiness-dependent check is needed for confidence, run it against an empty/fresh workspace and label the result as informational only.

## Implementation Notes

- Note `x86_64-apple-darwin` is intentionally absent from the matrix (ONNX Runtime prebuilt gap for the embeddings feature). Do not add it; call it out as a known platform limitation in the release notes instead.
- The `build` matrix uses `fail-fast: true` by design (S056) so a partial platform failure aborts the whole release — treat any single-platform failure as a full stop, not a partial publish.
- A minimal stdio driver can be a few lines of shell/PowerShell piping newline-delimited JSON-RPC into the binary; prefer that over adding a dependency.
- Estimated effort: ~2h.
