title: Distinguish terminal health-probe errors from transient not-ready in late-readiness recovery path
updated_at: 2026-08-27T07:17:24.7350849Z

Copilot PR review on #364 (137-F/130-S) found that shim::lifecycle::check_health collapses every fetch_health error (including a genuinely terminal IpcError::VersionMismatch / protocol-incompatible daemon response arriving after the initial readiness timeout) into a plain bool false, which both the request-triggered single-flight probe (src/shim/transport.rs ~L145) and the late-readiness monitor (src/shim/mod.rs ~L264) treat as transient/not-ready. This means a daemon that becomes reachable but is permanently protocol-incompatible would keep reporting recoverable: true / retry_after_ms forever instead of transitioning to a permanent terminal/degraded outcome, undermining the fail-closed contract for that narrow post-timeout scenario. Not fixed in-place under 137-F/130-S per its retro-staged verification-only scope (no production-logic edits). Proposed direction: give check_health/fetch_health a result-preserving return type so terminal health-response errors (protocol/version mismatch, malformed response) are distinguished from transient not-ready/unreachable errors, and route only the latter through the recoverable/cooldown path. A companion improvement: add a concurrent tools/call contract or unit test with a probe-count seam proving the session-wide single-flight mutex and 250ms cooldown actually suppress a second probe while one is in flight (not exercised by the existing sequential recovery test).
