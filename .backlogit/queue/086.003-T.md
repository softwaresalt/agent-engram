VERIFIED 2026-07-14: DaemonLock is workspace-rooted (direct.rs L74 DaemonLock::acquire(&ws_path)); direct.rs L88-90 explicitly acknowledges that when ENGRAM_DATA_DIR is shared across workspaces, two processes with different workspace roots (different DaemonLock paths) can race on the SAME CozoDB while migrate-down retracts calls_resolved_singleton rows and drops the resolution column (data-corruption risk). CHOSEN DIRECTION (Stage adversarial decision, DARK_MODE): FAIL-CLOSED — reject/refuse the destructive migrate-down when the resolved data directory is an external/shared dir not covered by the workspace-rooted DaemonLock, with a clear operator-facing EngramError explaining the shared-dir hazard. This is the conservative, minimal, non-destructive interim (refusing is safe; no silent corruption). DEFERRED ALTERNATIVE (recorded, not chosen now): a full exclusivity mechanism keyed to the RESOLVED database path and held by ALL writers for the whole migration — larger cross-workspace lock design; open a deliberation/follow-up if a real shared-data-dir multi-daemon use case emerges. TEST-FIRST ACCEPTANCE: (1) failing test first asserts migrate-down on a shared/external resolved data dir is REJECTED with the specific error and performs NO retraction/drop; (2) migrate-down on a normal workspace-owned dir still succeeds and remains idempotent; (3) error message names the shared-dir condition and remediation. IMPL NOTES: detect shared/external resolved dir (resolved DB path outside the workspace-rooted lock domain); reject before any retract/drop; no unwrap/expect.
