Plan unit F20 - request entry order and background activation. Implement `src/daemon/request_entry.rs` against the F04a seam with this exact order:

frame -> resolve descriptor -> authorize -> mode-gated capped metadata probe -> maybe-activate -> capture current `Arc<ReadRequestContext>` -> dispatch.

This is the SOLE request-context capture site and the SOLE admission authority in the daemon. Request-entry reconciliation is also the sole activation trigger (R48) - there is no control endpoint and no notification path.

`_health`, `_shutdown`, unknown methods, and refused methods must NOT trigger activation.

Execution posture: test-first.

<!-- BEGIN:acceptance-criteria -->
- The request entry order is exactly frame, descriptor, authorize, capped metadata probe, maybe-activate, capture Arc, dispatch.
- The metadata probe is mode-gated and capped so it cannot become an unbounded per-request cost.
- `maybe_activate_newer` is called before the context Arc is captured, never after.
- Exactly one context Arc is captured per request; dispatch uses that captured Arc and never re-reads global state.
- `_health` does not activate.
- `_shutdown` does not activate.
- Unknown methods do not activate.
- Methods refused by the capability gate do not activate.
- `request_entry::admit` is the only admission authority; no other code path admits a request.
- `tests/integration/request_entry_activation_test.rs` asserts each non-activating method class explicitly.
<!-- END:acceptance-criteria -->
