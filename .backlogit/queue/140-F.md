Removing the opt-in `agent-intercom` capability pack from this workspace surfaced two upstream defects in autoharness v1.5.0 (source repo `C:\Source\GitHub\autoharness`, `main` @ `2661c1c8`). Both were deliberately NOT worked around in engram beyond the minimum, because template-identical output is correct output; the real fix belongs upstream.

Full analysis with evidence: `docs/compound/autoharness-optional-pack-content-not-gated-in-templates-2026-08-31.md`

**Gap A — unguarded directives in two skill templates.** Autoharness templates are plain `{{VAR}}` substitution with no conditionals, so pack content relies on hand-written "When the `agent-intercom` capability pack is installed, ..." prose guards. Two templates omit the guard:

- `templates/skills/review/SKILL.md.tmpl:13` — "Call `ping` at session start." sits under a `## Agent-Intercom Communication (NON-NEGOTIABLE)` heading, so a pack-less install ships a NON-NEGOTIABLE instruction to call an uninstalled tool.
- `templates/skills/doc-review/SKILL.md.tmpl:38` — same sentence, wrapped.
- `templates/skills/review/SKILL.md.tmpl:80` and `doc-review/SKILL.md.tmpl:80` — `gated_auto` rows name `agent-intercom approval` as the default owner of an entire approval class.

Internally inconsistent with autoharness own model: `PACK_ASSERTIONS.review_intercom_workflow` gates that section on the pack being enabled, proving it is understood to be pack-scoped.

**Gap B — foundation assertion hard-coupled to an opt-in pack.** `src/autoharness/verify_workspace.py:454`, inside the unconditional `FOUNDATION_ASSERTIONS`, requires a literal `### agent-intercom` heading in `.github/copilot-instructions.md`. A workspace that legitimately disables this opt-in pack (`default_in_preset: []`, `mcp_requirements: []`) cannot delete the section without failing a foundation check. `### agent-engram` in the same assertion has the same latent defect.
