THIS IS THE DESIGNATED FIRST TASK OF THE SHIPMENT. Revision 4 shipped a backlog whose executable task cards lagged the canonical plan - the cards are what Ship actually executes, so safety requirements that existed only in plan prose would simply not have been implemented, and the task's own acceptance check would still have passed. A plan-only fix does not repair that class of defect; a mechanical parity check does. (R2, H30)

Walk the "Task-plan acceptance parity matrix" in the plan. For every canonical definition, confirm the owning task card states the requirement in its own acceptance criteria. Record the result as a parity note. ANY MISMATCH HALTS THE SHIPMENT BEFORE IMPLEMENTATION BEGINS and is returned to Stage - Ship does NOT silently reconcile a card against the plan, because "which one is right" is a planning decision, not an execution decision.

NOTE ON DEPENDENCIES: this task deliberately carries NO outgoing dependency edges. Adding edges from T14 to the roots would re-block 143.009-T's test-first red phase, re-introducing the H26 defect. Its first-ness is an instruction, not a graph edge.

ACCEPTANCE CRITERIA
1. Every row of the parity matrix is checked and its result recorded (MATCH / MISMATCH: <detail>).
2. Every canonical definition marked "blocking" in the matrix is present in at least one task card's acceptance criteria, BY NAME.
3. Any MISMATCH halts the shipment and is reported to Stage; implementation does not start.
4. The parity note names the plan revision it was checked against.
