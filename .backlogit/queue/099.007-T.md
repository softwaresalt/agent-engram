<!-- BEGIN:acceptance-criteria -->
- A queued MCP sync_workspace request that carries backfill_python_canonical=true still triggers the canonical backfill when it drains.
- Concurrency behavior of the pending-sync drain path is preserved (no lost or duplicated syncs under overlapping requests).
- Regression test covers: backfill request queued during active indexing -> backfill actually runs on drain.
<!-- END:acceptance-criteria -->

<!-- BEGIN:description -->
When an MCP sync_workspace({backfill_python_canonical:true}) request arrives while indexing is already in progress, write.rs coalesces it into a boolean pending_sync flag (set_pending_sync / take_pending_sync). drain_pending_sync then runs an ungated sync, so the backfill intent is lost and the canonical re-extraction migration silently never runs on the MCP path. The CLI path (engram index/sync --backfill, fixed in 82488eae) is unaffected; this is the MCP-path analog of that footgun. Not a false edge — the zero-false-edge invariant is intact — but a real P1 liveness gap.
<!-- END:description -->

<!-- BEGIN:implementation-notes -->
Boolean pending_sync (src/tools/write.rs:258-265; src/daemon/ipc_server.rs pending_sync call sites) must carry the backfill intent through drain_pending_sync/take_pending_sync rather than collapsing to a plain bool. Options: (a) pending_sync: Option<SyncIntent>; (b) separate pending_backfill AtomicBool checked in the drain. Update tests at src/tools/write.rs (pending-sync drain tests) and ipc_server.rs. Concurrency-sensitive: touch the drain path carefully. Source: PR #288 Copilot review comment 2 (write.rs:293).
