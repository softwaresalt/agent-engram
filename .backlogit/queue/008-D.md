# Branch DB seeding — eliminate full re-index on first branch sync

## Problem Frame

<!-- BEGIN:problem-frame -->
Each branch receives an empty CozoDB SQLite database at
`.engram/cozo/{branch}/engram.db` when first accessed (`connect_db` in
`src/db/cozo_backend/mod.rs`). Because the DB starts empty, the first
`sync_workspace` call on any new branch is a full re-index of the entire
workspace — even when the branch diverges from `main` by only a handful of
files.

`sync_workspace` (`src/services/code_graph.rs:627`) is already incremental:
it skips files whose content hash matches the stored value. The optimization
gap is exclusively on the **first sync** of a new branch, where no stored
hashes exist. On a large codebase this can take many seconds or minutes even
though 95%+ of the symbol graph is identical to `main`.

Observable evidence: `.engram/cozo/` already contains many branch-specific
DB files (`feat__*`, `chore__*`, `stage__*`), confirming that branch
proliferation is real and the cost compounds across an active dev workflow.

The question is whether seeding a new branch's DB from `main`'s existing DB
(plus a differential sync of branch-specific file changes) is safe, correct,
and worth the implementation complexity.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
**Option A — Copy-and-sync (the stash proposal)**
When `connect_db` creates a new branch directory and finds that
`.engram/cozo/main/engram.db` exists and is not locked, copy it to the new
branch path before opening CozoDB. Then run `sync_workspace` normally; the
existing content hashes from `main` mean only files changed on the branch
will be re-indexed.

Pros: Minimal implementation surface (one copy before `DbInstance::new`);
reuses existing incremental sync logic with no changes; fastest first-sync
for branches close to `main`.

Cons: SQLite file copy safety — must guarantee no in-flight transaction
(journal files absent or WAL checkpointed); copy happens inside
`spawn_blocking`, so a large DB could block the thread pool briefly; stale
symbols from `main` for files deleted on the branch require deletion logic
in `sync_workspace` to work correctly; introduces an implicit dependency on
`main` being indexed first.

**Option B — Incremental git-diff seeding**
Instead of copying the DB, compute `git diff main..HEAD --name-only` at
first-sync time to identify changed files. Treat all other files as already
indexed (insert their hashes into the empty DB without parsing). Then only
parse and index the changed files.

Pros: No file copy, no SQLite safety concern; avoids carrying stale main
symbols into the branch DB; explicit and auditable.

Cons: Requires git integration in the sync path (already present via
`src/services/git_graph.rs` but not wired to `sync_workspace`); the "insert
hashes without parsing" step still requires reading file content for hashing,
which may not be much cheaper than a full parse for small files.

**Option C — Status quo + deletion correctness audit**
Keep per-branch empty DBs but audit whether `sync_workspace` correctly
handles file deletions on a branch (symbols removed from the graph when a
file is deleted or moved). If deletion is already correct, no optimization is
needed at this stage; if not, fix deletions first before adding seeding
complexity.

Pros: Lowest risk; sharpens understanding of the actual correctness baseline
before adding optimization.

Cons: Does not address the full-re-index performance cost.

**Option D — Shared main read replica + branch delta DB**
`main`'s DB is opened read-only; branch writes go to a small per-branch
delta DB; queries merge both at query time. Most memory-efficient for many
branches.

Pros: Near-zero branch creation overhead; shared storage.

Cons: Requires query-layer changes across all CozoDB relation reads; high
implementation complexity; incompatible with current single-DB architecture
in `cozo_backend`.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
**Option C** — deletion-correctness audit first.

Rationale: Before seeding a branch DB from `main`, `sync_workspace` must
correctly remove CozoDB symbol and edge records when files are deleted. If
it does not, a seeded branch DB inherits stale symbols that incremental sync
cannot recover. Confirming correctness is the lowest-risk first step.

If the audit passes (deletion is correct), Option A (copy-and-sync) is the
preferred implementation path. Option B (git-diff seeding) is the fallback
if SQLite copy safety proves problematic on any supported platform.

**Execution package**: Feature `060-F` / Task `060.001-T` / Shipment `046-S`.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. Does `sync_workspace` currently remove CozoDB symbol/edge records when a
   source file is deleted from the workspace? (Check
   `src/services/code_graph.rs` around the deletion path — critical for
   Option A correctness.)
2. Is the CozoDB SQLite file safe to copy with `std::fs::copy` while the
   main-branch DB is open but idle? WAL mode may leave a `-wal` or
   `-journal` sidecar that must also be copied (or the checkpoint must be
   flushed first).
3. What is the actual measured full-re-index time on the current workspace?
   If it is under 5 seconds, the optimization may not justify the added
   complexity.
4. When a branch is renamed or force-pushed (branch directory name stays the
   same), does the seeded DB become stale in ways that incremental sync
   cannot recover from?
5. Should branch seeding be opt-in (config flag) or automatic? An opt-in
   flag reduces risk during initial rollout.
<!-- END:open-questions -->

  Option A's copy step would be inserted, before `DbInstance::new`.
- `src/services/code_graph.rs` — `sync_workspace` at line 627;

  verification.
- `src/services/file_tracker.rs` — content-hash tracking; the hash store
  that makes incremental sync work; seeded DBs would inherit these hashes
  from `main`.

The `.engram/cozo/` directory already shows the scale of branch proliferation
on this repo: at least 15 named branch subdirectories observed. The `main`
DB exists at `.engram/cozo/main/engram.db` and is the natural seed source.

If Option A is chosen, the implementation task is narrow: one new function
`seed_branch_db_from_main(data_dir, branch_safe)` called inside
`connect_db` before `DbInstance::new`, guarded by existence checks for the
main DB and absence checks for the branch DB.
