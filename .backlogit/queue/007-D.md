# Evaluate HNSW for Engram vector search

## Problem Frame

<!-- BEGIN:problem-frame -->
Determine whether Engram already uses HNSW for vector search, whether adopting it would improve the product, and what trade-offs or constraints should drive the decision.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
1. Keep the current vector search approach if it already meets latency, recall, and operational goals.
2. Adopt HNSW if current search is not approximate-nearest-neighbor based and HNSW materially improves startup/query performance.
3. Defer adoption if persistence, update cost, implementation complexity, or dependency risk outweigh benefits.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Run a bounded spike that first verifies the current implementation, then evaluates HNSW adoption criteria against repository scale, index maintenance cost, retrieval quality, and implementation complexity before recommending adoption or avoidance.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
Is the current backend already using HNSW internally? What repository sizes and embedding counts make HNSW beneficial here? How would HNSW affect index build/update time and on-disk footprint?
<!-- END:open-questions -->

## Notes

<!-- BEGIN:notes -->
This is a research-first item. The output should be a decision-ready recommendation, not an implementation commitment.
<!-- END:notes -->
