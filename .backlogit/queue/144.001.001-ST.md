ROOT OF MEASUREMENT-ONLY WORKSTREAM B. A durable, workspace-contained sink for startup records plus the phase_started/phase_completed record protocol. Nothing else in 144-S may start before this exists.

WHY: the existing "CozoDB startup timing" log in connect_db is emitted only AFTER the spawn_blocking closure returns, so a STUCK daemon emits nothing at all, and .engram/logs/ has had no durable daemon sink since 2026-07-05. The evidence goes missing in exactly the failure it exists to explain.

AC1 (DURABLE INCREMENTAL WRITES): records are appended and durably flushed AS EACH RECORD IS PRODUCED, never only in a terminal aggregate line. A test kills the process mid-bootstrap and asserts the already-emitted records are present, complete, and parseable.
AC2 (SINGLE SERIALIZING WRITER, NON-NEGOTIABLE): ALL startup records pass through ONE serializing writer. Concurrent emitters - the blocking bootstrap thread, the heartbeat task, and the readiness path - MUST NOT interleave partial records. A concurrency test proves no torn and no interleaved lines.
AC3 (PHASE_STARTED / PHASE_COMPLETED PROTOCOL): the record protocol defines a durable phase_started record emitted BEFORE each potentially blocking phase is entered and a phase_completed record emitted AFTER it returns. A phase that never completes therefore leaves a phase_started with no matching phase_completed, which is the ONLY way a mid-stall daemon can be attributed. A test asserts the unmatched-started shape is produced when a phase is killed mid-execution.
AC4 (VERSIONED SCHEMA): every record carries an explicit schema version, so a later shape change is detectable rather than silently misparsed, and so 144.001.004-ST classification can be derived FROM THE SINK ALONE with no live process.
AC5 (FLUSH BEFORE RENAME OR ROTATION, AND WORKSPACE CONTAINMENT): flush precedes any rename or rotation, and the sink path resolves under the workspace .engram/ tree (constitution III/IV).
AC6 (B-OWNED, DECOUPLED FROM WORKSTREAM A): this sink does NOT replace, wrap, or depend on the A-owned 143.004.001-ST terminal-cause sink, and 143.004.001-ST does not depend on this one. The two shipments stay decoupled; verified by an explicit statement of the module's dependencies.
