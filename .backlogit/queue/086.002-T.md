Add a bounded reopen-retry to connect_db (src/db/cozo_backend/mod.rs L110) for the transient 'database is locked' (SQLITE_BUSY) surfaced on rapid sequential reopen of the same branch DB (Windows lock-release lag), because cozo 0.7.x unwraps internally. VERIFIED 2026-07-14: an intra-process serialization mutex (connect_db_open_lock, L187) already exists for the U015-FLK1 residual, but it does NOT retry on OS-level lock-release lag across processes/handles — a bounded reopen-retry is still required. A bounded retry in connect_db was reverted from PR#238 (outside 081-F freeze-scope) and replaced with a test-scoped retry; deliver it here as a separately-tested reliability change on the shared DB open path. TEST-FIRST ACCEPTANCE: (1) failing test first reproduces/injects a transient busy on reopen and asserts connect_db succeeds within the bounded retry budget; (2) retries are bounded (max attempts + backoff cap) and give up with a clear EngramError, never an unwrap panic; (3) no regression to the existing connect_db_open_lock serialization tests (L298/L318). IMPL NOTES: bounded exponential backoff with jitter; classify only busy/locked as retryable; keep forbid(unsafe_code); no unwrap/expect. Single-width: src/db/cozo_backend/mod.rs only. BLAST RADIUS: shared DB open path used by every daemon+direct operation — ELEVATED; requires plan-harden + monitoring/rollback note. Interim SQLITE_BUSY mitigation — relates to blocked 041.002-T (removal when cozo>=0.8). Related stash 100EACD8 (archived under 025-S). Source stash 30CE5DD6 (Copilot PR#238 comment 3563254094).
