# Same-file duplicate function-name shadowing: fail-closed on ambiguous direct-edge target

## Problem Frame

<!-- BEGIN:problem-frame -->
find_function_id (src/services/code_graph.rs:2988, first-match `.find()`) resolves the direct-edge callee target by NAME ONLY. When a file has >1 top-level def of the same name (legal in Python where the last def shadows/wins; also reachable in Rust via same-name defs in different inline `mod` blocks per file), the two direct-edge minting sites — index path (~code_graph.rs:1644-1645) and sync path (~2522-2523) — bind a bare call to the FIRST (earlier/shadowed) def instead of the effective target, minting a WRONG call edge. This violates 013-D (no-false-edge) and 082-F (target-correctness). The existing Python `is_contested` guard (code_graph.rs:332/334) catches import/rebind ambiguity via `is_ambiguous` but does NOT catch two same-name top-level defs in the same file's `function_ids` vector. Same-file bare calls take the DIRECT-edge path BEFORE any canonical/singleton post-pass, so 096-F's canonical resolver cannot fix this — the canonical index fails closed on duplicate canonical_path rather than applying last-wins. Newly EXPOSED (not introduced) by Python 094-F; the SHARED consumer also affects Rust same-name-in-different-inline-modules-per-file. INDEPENDENT of FE8B3B2D/096-F.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
Option A — Fail closed on same-file same-name ambiguity (RECOMMENDED): when >1 candidate shares the callee name in this file's function_ids, do NOT mint a first-match direct edge; route to staging (the cross-file post-pass already skips ambiguous/unmatched names to bound false edges, code_graph.rs:1764-1766) or drop fail-closed. Language-agnostic; preserves 013-D across BOTH Rust and Python; mirrors the existing cross-file singleton "skip ambiguous" precedent and the canonical duplicate_canonical_path fail-closed. Cost: recall for the rare legitimate same-file redefinition effective call is deferred (documented v1 limitation). || Option B — Source-order / last-wins semantics: return the LAST matching def (Python last-def-wins). Recovers recall + correctness for the Python case, BUT last-wins is UNSOUND for the shared consumer: in Rust two same-name defs in different inline `mod` blocks per file are DISTINCT targets disambiguated by module path, not source order — blanket last-wins would MINT A NEW WRONG Rust edge, trading one false-edge class for another. Requires language-gated logic + per-language correctness proof; higher blast radius; violates the "keep the shared resolver language-agnostic and fail-closed" principle.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option A — fail-closed on same-file same-name ambiguity, language-agnostic. Introduce an additive ambiguity-aware resolver (e.g. find_unique_function_id returning None / a typed reason when >1 same-file same-name candidate exists) used ONLY at the direct-edge callee-resolution minting sites; leave find_function_id byte-identical for all other consumers (caller attribution, resolve path, and the 5 other call sites). Apply symmetrically at the index (~1644) and sync (~2522) sites so both indexing and incremental sync fail closed identically. Mandatory Rust-path regression test proving no recall regression on legitimate unique-name same-file calls AND correct fail-closed on an adversarial same-file duplicate-name corpus. A Python-only last-wins recall recovery is a documented, deferrable follow-up — explicitly NOT v1.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
(1) Should the ambiguity guard also cover the CALLER side (same-file duplicate enclosing-function name -> uncertain edge origin)? Recommend YES — symmetric fail-closed to fully honor 013-D. (2) Confirm function_ids vector preserves source order (only needed IF a future last-wins follow-up is pursued; not required for fail-closed v1). (3) Should the fail-closed drop increment cross_file_edges_dropped or a dedicated same-file-ambiguous counter for observability parity with the post-pass?
<!-- END:open-questions -->
