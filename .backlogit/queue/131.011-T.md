Make the unchanged 131.010-T RED GREEN in the daemon lifecycle runner. Move the retained explicit provider owner into one dedicated `std::thread` cleanup worker. The daemon awaits only the worker's phase/completion channel under an application-owned five-second total wait. The worker may outlive that wait; the code must not join it or claim that synchronous SDK cleanup was canceled or completed.

<!-- BEGIN:acceptance-criteria -->
1. 131.010-T is complete with compiling RED evidence and remains the explicit dependency. 2. Exactly one native worker is launched after the daemon future ends; do not use Tokio `spawn_blocking`, a runtime-owned task, or a joined thread. The explicit provider owner moves into the worker, which invokes `force_flush` once and, if that call returns `Ok` or `Err`, invokes `shutdown` once. If `force_flush` never returns, shutdown is not falsely reported as attempted. 3. `OTLP_CLEANUP_WAIT_TIMEOUT = Duration::from_secs(5)` bounds only the daemon's wait for the complete worker sequence. `OTLP_EXPORT_TIMEOUT = 5 seconds` remains a separate per-export-future limit and cannot establish a whole-operation bound. The completion wait uses a monotonic Tokio deadline and a phase/completion channel. 4. On deadline, the runner drops its receiver, does not join, and reports wait limit, last phase (`not_started`, `force_flush`, or `shutdown`), `completion=unknown`, and `worker_detached=true`. Resources, queued spans, exporter I/O, and method completion may remain unresolved until process termination. A worker panic/channel close is a distinct visible cleanup-worker failure. 5. A clean daemon returns cleanup failure/timeout. If both daemon and cleanup fail, the daemon error remains primary and the complete cleanup diagnostic is logged to stderr before return. No retry occurs. 6. The unchanged 131.010-T command passes deterministically. Because the worker is a detached native thread rather than a Tokio blocking task and the daemon never joins it, the main future can return at the deadline, Tokio can tear down its async tasks, and normal binary process exit terminates the residual thread. This guarantee applies to daemon wait, not to SDK call cancellation/completion; embedding the runner in a process that continues running is prohibited without a reaper redesign. No provider-construction, endpoint, attachment, Cargo, lockfile, config, or unrelated lifecycle edit is included.
<!-- END:acceptance-criteria -->
