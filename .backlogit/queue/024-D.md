# Use the public cap-fs-ext Windows identity bridge

## Problem Frame

<!-- BEGIN:problem-frame -->
The 121-S closure treated Windows same-object proof as blocked by unstable or unsafe handle APIs. A focused spike checked the exact pinned dependency sources.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
A) keep the Windows proof disabled; B) import cap-primitives internal _WindowsByHandle; C) use public cap_fs_ext::MetadataExt over handle-derived capability metadata.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Choose C. The already-pinned cap-fs-ext 4.0.2 safely exposes dev()/ino() for cap_primitives Metadata on Windows, internally bridging by-handle identity. No unsafe or dependency change is needed.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
Record filesystem type during verification. cap-fs-ext documents a ReFS 128-bit file-identifier caveat, so the initial gate is NTFS and ReFS remains an explicit residual. Multi-model adversarial review is still required before harvest.
<!-- END:open-questions -->
